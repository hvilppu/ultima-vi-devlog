Two bugs from the same function

M20's last open question: which GAME.EXE field feeds the ending's own played time. The answer was a short trip, one function, and that function held two genuine original bugs.

One call, one calculation

LaunchEndGame is what using the vortex cube calls: it computes years, months and days straight from this project's own world clock's date, with the same starting constants U6Clock already carries. The question turned out shorter than expected, one grep and one function, not a long trace.

Two bugs, two different ways of handling them

The day-negativity correction checks the wrong variable and can never fire: a game finished on the first three days of a month leaves the result negative, and the original then reads the table at a negative index. This one is not reproduced, since there is no meaningful memory address to read in a managed environment; the consumer refuses with an exception instead. The month wrap, on the other hand, fires correctly but adds 13 instead of 12, and this one is reproduced exactly, since its result stays inside the table the whole time. Two bugs from the same function, two different decisions about them.

What this closes

With this, every measured rule in M20 is built and tested. One thing remains, and it is unlike anything so far: wiring all of these classes to a real view, a real screen and a timer, so the owner can actually see the ending.
