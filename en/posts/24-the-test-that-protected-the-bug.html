The test that protected the bug

I set six agents to break my own claims about what the world adapter's seven answering members do. Not one claim survived intact. The worst finding was not in the code but in a test I had written an hour earlier, which protected the same bug I had just fixed next door.

Why a refuter and not a reviewer

The last post described three defects in one class. All of them had the same shape: I read the surrounding code instead of the opcode handler whose rule I was implementing. None of them failed a test. None of them looked wrong.

That last point is the one that decides it. A reviewer reads the implementation and asks whether it is sensible, and all three were sensible. A refuter reads the original first and then goes looking for where the implementation disagrees. That is a different question, and the only one that catches this.

Six refuters, one claim each, told to break rather than confirm. The structure is now a permanent part of the project.

The one that stings

The gate on a character's name was wrong: I gated it on party membership, where the original gates on the top bit of the character status byte. I fixed it, wrote the class its own tests, and wrote it down.

In the same file, eight lines further down, sat IsInParty, which searched the party places for the character number. The original asks five conditions there: the player commands them, they are on screen, and they are not dead, asleep or paralysed. A search of the places is none of those.

So it is the same mistake, in the same file, in the same pass. I fixed one and wrote the other a test that pinned the wrong rule as correct. By the time a refuter found it, the suite held two tests actively defending a guess.

A live bug, measured

The strongest report built its own probe against the real export. The composer tested the light on the square the object stands on. The original tests the square each of the object's tiles lands on, separately.

The difference is everything wider than one square. An object standing in the light does not reach into the dark, and one standing in the dark does reach into the light. I measured both directions by putting the old gate back: 

dark squares carrying an object     897  ->  0
lit squares carrying an object    34193  ->  35073

897 is exactly the number the refuter arrived at independently. A character standing in the dark was counted as on screen whenever a wide object happened to stand next door.

A claim of rigour that did not survive checking

This is the one that changed how I think about what measuring takes.

The plan said of flag numbers eight and above that the chosen reading works and that a plausible wrong one fails the test. The project's own rule demands precisely that second half, and I had written it down as though it were done.

The test uses the values 8, 31 and -1. Under the wrapping reading those give shift counts of 8, 31 and 31 on a sixteen bit value, which is zero every time. 

value   my reading    wrapping reading
    8   nothing       nothing
   31   nothing       nothing
   -1   nothing       nothing
   32   nothing       bit 0        <- the only discriminator, untested

So the discriminator does not discriminate. And which reading is right depends on the target CPU and on what the compiler emitted, neither of which is in the repository. The right answer is undetermined, and that is what it says now. It is unreachable in the shipped data, because all 788 flag sites use bits 0-7.

The knowledge was already in the building

One of the two name instructions answers with the word "you" when the character is the Avatar. I accepted the parameter and threw it away.

The rule is written correctly in this repository's opcode table, in English, two files away. The interpreter passes the flag correctly. The world ignores it. So the implementation guessed an answer that was written down beside it.

Three too many, and the same trap as before

A refuter put the flag writes at 423, not the plan's 422. I measured for myself and got 425 writes and 366 tests: three instructions too many, one for each of the three flag instructions.

A mistake that uniform is not a coincidence, and it is a trap this project has already recorded: the character number sits in byte one of the script, and three characters carry a number that is also a flag instruction. 

character 164 = 0xA4 = set flag
character 165 = 0xA5 = clear flag
character 171 = 0xAB = test flag

The same class of fault once inflated the count of printing instructions, through character 181 being 0xB5. Skipping the header removes exactly those three, and the number is 423. These figures had no test at all until now.

The same pass corrected a framing that was wrong everywhere: the met flag is written 274 times, and that is 210 sets and 64 clears. A quarter of the writes clear it.

172 did not move

I expected it to fall, because IsInParty is far stricter now. It did not.

That is a result and not a disappointment, and it confirms what post 23 said about the number: it is a floor on what is broken, not a ceiling on what works. A wrong answer does not stop a conversation, it sends it down the other branch. That is exactly why the number is no measure of completeness, and exactly why the test asserts as much.

The refuters were themselves wrong twice

One claimed the vehicle exemption was unrecorded. It is recorded in three places, but in Finnish, so an English search found nothing. Another filed a measurable figure as unmeasurable, because the test lives in Unity's folder; it runs headlessly with one command.

Each turned a checkable question into a confident wrong sentence, which is the one thing a refuter must not produce. Both are now mandatory facts in the instructions, and the rule says a refuter's finding is confirmed by me before anything is changed on the strength of it: a wrong refutation that gets fixed makes correct code incorrect.
