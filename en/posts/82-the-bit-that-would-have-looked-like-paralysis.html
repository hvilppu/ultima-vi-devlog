The bit that would have looked like paralysis

This slice is thinner than most: it measures almost nothing new. It connects one status bit to three gaps that three earlier slices had already measured and written down as waiting for exactly it. The interesting part is not what got built, it is what would have been built wrong without one warning.

Two bytes, the same number, a different meaning

This project keeps two separate status bytes for a character, exactly as the original does: one whose bits are "owned", "charmed" and "temporary", and another whose bits are "paralysed", "asleep", "poisoned" and "dead". The invisible bit belongs on the first byte, at bit value 0x02. The second byte's own bit value 0x02 is paralysed. The same number, two completely different things, depending on which byte it lands in.

A creature written into the wrong byte does not crash, does not throw, does not look broken in any obvious way. It reads as paralysed. The game stays playable, the monster freezes in place, for an entirely different reason than a paralysing attack. This is exactly the kind of mistake that surfaces a long time later, far from where it was written, if it surfaces at all. That is why this one line gets its own discriminator: a test that makes the same creature invisible and paralysed in turn, and neither is ever allowed to read as the other.

One bit, three open questions

The player's own attack command once measured all six of COMBAT_canSee's rules in full, but could only build one of them: the viewer and the target must share a level. The other five stayed named, because nothing carried the field they needed: no invisible bit, no dragged-under state, no "ignore" flag read for this purpose. The slice that applies a hit left clearing invisibility on death as a named gap for the same reason. The spell slice measured the reveal spell completely, ring move included, and never applied it, because nothing ever called it.

Three different slices, three different documents, one shared missing piece: the bit itself. That is what makes this slice thin as construction and still worth doing: it invents nothing, it just hands already finished work its last piece.

Six rules, one place

All six sight rules now live in one Unity independent class, U6CombatSight.CanSee, tested in both directions for each rule on its own. Rule two is the one that reads oddly in play but is measured precisely: a player controlled viewer always sees another player controlled target, even an invisible one. Your own party member never vanishes from your own eyes; an invisible monster does. This is a pair that has to be tested together, because tested apart either one would look correct even with the other missing entirely.

The view's own CanSeeCombat stays a delegate exactly as the player attack slice left it; it now simply forwards to this new class. No targeting code knows or needs to know how many of the six rules the delegate happens to answer.

Death and the spell, at exactly the same spot

The original clears invisibility on death in one line, after the experience is computed and before the corpse shape is chosen. That is now the same line in this project, in the same order, touching neither neighbour. The reveal spell's own ring is not destroyed, it moves from the equipped slot to the inventory slot, on exactly the original's own condition: only when the ring is currently worn.
