Four letters, in the wrong place

The conversation engine is finished. On the way it turned out that the story people tell about this game's parser is true, just not where anyone thinks it is.

Two instructions were left. One writes into an array inside the script, the other searches an array for a string. With those done, the count of unimplemented instructions in the corpus test fell to nought.

A script is working memory

The writing instruction forced a decision I had been putting off. To the original, a loaded script is editable working memory: an assignment to an array changes the running script, and the change lasts as long as the conversation does. To me a script was only bytes to read from the export.

There were two options. Copy the script into a writable buffer for the length of a conversation, or keep the changes in a separate overlay that every read consults. The second would not have touched a single signature, but it is a mechanism the original does not have, and it would slow the read path down for everybody.

I chose the copy. Faithfulness is the whole point of this project, and a writable buffer is what the original does. The largest script is 7249 bytes, so the cost is not worth weighing. Talking to the same character again starts from the unchanged original, because the original reloads the script every time as well.

I expected the change to spread everywhere. It did not: only the writing path needed a writable reference, because a writable one converts to a readable one by itself. The reading side was untouched.

The test for this is not "it does not throw" but the script reads back what it wrote: the assignment changes the array, and a later expression in the same script reads the changed value. That is the entire reason the buffer was needed, so it is the thing to test.

Four letters is real

In post 16 I wrote that the engine does not shorten keywords to four letters, and that the saying came from how the scripts happen to be written. That is still true of keyword matching.

But the string search does shorten. It compares an array entry over at most four characters, and a shorter entry over its own length.

So the saying is not invented. It describes an instruction the shipped scripts use twice, and not the matching that every conversation in the game depends on. The story is true and in the wrong place at the same time, which is my favourite kind of finding.

The search revealed a second difference. There is no star rule: the original checks for a star where it matches keywords, not in the comparison. So I had to split my comparison in two, otherwise every search entry beginning with a star would have matched anything.

And a search answers with the number of entries when nothing matches, not minus one. Minus one would be the obvious choice and would read as the last entry in anything that indexes with the answer.

Wrong three times, caught three times

This slice was humbling about tests. Three times a test failed, and every time the fault was in the test rather than the code.

In an expression, reading an array takes its index from the stack and has no "no index" form, which I had used. An array word is signed, so the value I wrote read back negative. And in the star test I expected index one, when the right answer is the entry count: if the star does not answer, nothing answers.

And a fourth, which the audit caught

The pre-commit check looks for loose assertions, and it pointed at one: greater than zero. I went and looked at what the test actually ran.

Its name promised that a search runs to the end of the script when the terminator is missing. It did no such thing. It stopped three entries in, at a zero byte, which reads as an empty entry, and an empty entry matches anything. The test was in the wrong place and passing anyway.

I rebuilt the script so that nothing after the array contains a zero byte, which makes it really run to the end, and gave the empty entry a test of its own. One loose assertion became two exact ones, and a rule I had not noticed came out of it.

One instruction still throws: the value search. No script uses it, so an implementation could not be checked against anything, and an unchecked one would look finished without being so. A clear refusal is more honest.
