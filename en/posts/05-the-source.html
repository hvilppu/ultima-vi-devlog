Rebuilding Ultima VI

Notes from a 1:1 reimplementation in C# and Unity.

← all posts · 05

Someone already did the hard part

A decompilation of the original exists. It removed the project's biggest risk and immediately caught a bug of my own.

Data files can be reasoned about from the outside. Rules cannot. There is no amount of staring at bytes that tells you how damage is calculated, and a 1:1 reimplementation cannot settle for "close enough", so at some point the executable has to be read.

The main binary is not friendly. Its relocation table is empty and the entry point sits almost at the end of the file: the classic shape of a self-extracting stub. No known packer signature matches, so it looked like a bespoke one, and unpacking it was budgeted as the single riskiest task in the whole plan. If that had failed, the 1:1 goal would have failed with it.

It turns out that work has already been done, publicly, by someone else. A decompilation of the DOS version exists as readable C that rebuilds the original executable with very few differences. Roughly three hundred functions and four hundred globals carry meaningful names. The front-end and endgame programs are there as well.

It even targets version 4.5, which is exactly the version the disk labels in my own copy identify. The project's largest unknown stopped being an unknown.

Reading it without copying it

That source carries no licence, and it is derived from someone else's game regardless. So the working rule for this project is strict and written down:

Read a function. Write down what it does, in your own words, as a note. Implement the C# from the note, not with the original on screen. Then verify the behaviour against the real game.

That middle step is not bureaucracy. It serves three purposes at once. It keeps legal distance. It protects the code quality: a line-by-line translation of 1990s C would drag segmented pointer arithmetic and three-letter globals straight into a modern codebase. And it is a comprehension test: if you cannot write the rule out in a sentence, you do not understand it well enough to reimplement it.

Nothing from that repository is committed here. It lives in an ignored directory and is treated as documentation.

What it caught straight away

The file holding tile behaviour is 7,168 bytes. Earlier I had read it as three tables of 2,048 bytes with a 1,024-byte remainder at the end, which is a reasonable guess that fits perfectly. It is also wrong. The real layout is four tables of different sizes, and the odd one sits in the middle:

This is the failure mode that makes reverse engineering slow. Nothing crashes. No range check fires. You get bytes back, they vary per tile, they look like flags. The error would have surfaced weeks later as movement behaving oddly in ways nobody could reproduce.

It is worth being clear about whose mistake that was: mine, not the original's. It went into the project's own notes, not into the log of original bugs.

Named at last

With the layout right, the bits have meanings. Terrain carries wet, impassable, wall and damaging, plus four edge bits. Display carries opaque, window, foreground and blocks-missiles, and its lowest two bits are not flags at all but a light emission level, which would have been easy to misread as two more booleans.

I verified each one against the name table rather than taking it on trust. The damaging bit lands on traps, webs, spikes, lava and fire fields. The light level lands on magical items and glowing things; a fire field emits light level 2. The weight table gives zero for floor and earth, and sensible values for everything a player can carry.

Two of the twelve rule tables are now recovered. Ten to go, and the one I want most is the random number generator. Without matching it, verifying combat can only ever be statistical.
