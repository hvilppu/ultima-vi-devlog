Two Fields the Export Has Never Known

The last post built a bridge for objects. This is its pair, the same bridge for characters: the live U6CharacterData turns into OBJLIST's own bytes. Along the way two fields turned up that this project's own export chain has never known at all, and both needed measuring before either could be written.

A factory instead of a file

U6CharacterTable.ToBytes always only read its own fields, every one of them loaded from a file. The new FromLiveState is a factory for it that takes the same fields already assembled instead of parsed, and U6LiveCharacterTable.Build assembles them from the live character table. Two steps that had been ready as primitives with nothing calling them finally got wired in: the quest flag's own save, and a boarded member's position.

One field settled by counting, not by guessing

Amount, offset 0x0600, 512 bytes. Read straight from the real OBJLIST: every one of the 200 in-use character slots carries quantity 1, quality 0. Every one of the 56 unused ones carries 0, 0. A complete correlation with the flag the engine already tracks, so the rule needed no new state at all, only one condition.

The other field is this project's own, unconfirmed name

PathData, offset 0x1AF1, 256 bytes. A search of the whole decompilation under that name comes back empty. Measured directly: all 256 bytes are zero in the one real save available. Written as zero, but claiming no more than what was measured: not confirmed to stay zero for the whole game, only that it is zero in this one save.

The whole chain proved in one run

Real OBJLIST to this project's own exported characters.bin to the live U6CharacterData to U6LiveCharacterTable.Build: the result matches the original byte for byte, except a stored name's own unswept padding, which the export has never carried past the trimmed string. That is not a new gap, only the same already recorded one showing up somewhere else.
