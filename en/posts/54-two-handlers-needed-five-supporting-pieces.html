Two Handlers Needed Five Supporting Pieces

The first piece of M14's third slice is now built: entering combat, leaving it and a charm ending. The three handlers' own logic was already settled after the previous slice's measuring, but building them uncovered five missing pieces the logic leaned on that the character record did not yet offer.

A known rule does not mean the data already exists

COMBAT_begin, COMBAT_breakOff and COMBAT_stopCharm were portable as they stood, no open question about what they are supposed to do. Building them hit two bits and three fields that U6CharacterData did not read yet: a charmed bit, a backed up alignment, a party leader, a solo member and a place to save the original's mode. Every one of them had already been measured earlier or was readable straight out of the decompilation; nobody had written them out yet.

Two bytes that share a bit number

The charmed bit, 0x04, sits on the Status byte. That is a different byte from NpcStatus, whose own 0x04 means asleep. The same shape repeats for alignment: the backed up alignment uses mask 0x60 on the NpcFlags byte, while the live alignment uses the same mask on a different byte, NpcStatus. Either pair would be easy to get wrong by reading only the bit number and not its byte.

Runtime state that lives in no exported byte

SavedNpcMode keeps the behaviour that was in force before command mode took over, so breakOff can restore it. In the original it is a single global variable at address 0x2CC4, far outside the exported 130 byte game state block. So it is not something that should be saved to a file at all; it was modelled as a plain runtime property instead.

On the side: two tile bits for the next slice

U6TileBank gets two new queries, IsWindow and BlocksMissiles, both on the display byte's bits 0x08 and 0x20 under u6.h's own names. Of 2048 tiles, 27 are windows, 206 block a shot outright, and 9 do both. Neither is used by anything yet; they are waiting on COMBAT_Missile's own line of fire rule, which has not been measured.

One candidate bug, not reproduced

The original would read one place past the party array if the whole party is incapacitated at once when picking who gets control. A managed array cannot hand that value back, so this version falls back to place 0 instead, and the case is recorded as an open candidate bug, neither reproduced nor fixed.
