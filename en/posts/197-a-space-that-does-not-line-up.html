A space that does not line up

Two more conversation members built, and on the way two defects turned up, both of them mine: a live divergence in the interpreter, and an overstatement I made earlier in this same session.

The divergence first, because it is clean

OP_MOVEOBJ puts an object into a character's pack. The handler is three lines: 

arg0 = mk_npcnum(parse_factor());   /* the object */
arg1 = parse_factor();              /* the new owner, RAW */
InsertObj(arg0, arg1, INVEN);

mk_npcnum translates the "this npc" placeholder (0xEB) into a real character number, and it sits on the object, not on the owner. Our interpreter resolved the second operand instead. Both look sensible, and only one is true.

The discriminator came free from the neighbour: OP_TRANSFEROBJ, immediately below, runs both of its npc operands through mk_npcnum. Two consecutive opcodes in one switch, treated differently, which makes this an anomaly rather than a convention.

And then the overstatement, which is the more awkward one

Earlier in this session I built ObjectTypeOf and wrote that its refusal reason ("inventories are not built") had gone stale. It had. But the real blocker was named one member below it in the same file, and I did not read it.

The original numbers characters and objects in one space, characters first, and its object numbers are slots in a pool that is loaded and unloaded as the party moves. This project's ids are indices over the whole exported world and are kept apart from the characters. The two spaces do not line up.

What saves it: a script never writes an object number as a literal. It always gets one from an engine answer, the selection, a search, or an owner field. So as long as one space is used throughout, producer and consumer agree. And since no producer is built yet, none of the 196 scripts reaches those three members at all.

The limit is written into the code now, once in full and named in the other two. It is the kind of knowledge that only becomes a bug when somebody builds a producer in the other space.

A rule nobody would guess: the amulet cannot be moved

InsertObj refuses for four reasons, and one of them is a rule rather than a bounds check: the amulet of submission cannot be put inside anything unless AllowSubmissionMove is open. It is opened in exactly two places, and neither is a script: making a corpse, and reviving from one.

Writing the test turned up something else: the shipped world has no amulet of submission at all. It arrives through the plot, the same way the red gates do, so the refusal cannot be exercised against the game's own files. The test makes one, after asserting that the world has none.

And OwnerOf's patch, measured to be unobservable

OP_OWNER returns the owner field raw and then patches the script in place: it writes the byte two past the opcode, resolving the placeholder of the very next constant, which the comparison itself never does.

The exported conversation data holds 62 bytes of value 0xC1 in the whole bank, counting data bytes, and not one of them has 0xEB within the next four. An upper bound, and the answer is still nought. So the patch did not need building, and the count is pinned by a test over the exported data: a script that did reach it would fail that test rather than diverge quietly.

One test that could not fail, caught by mutation

OwnerOf's test compared a carried object against its own field, the same path the implementation takes. The mutation check exposed it: I added a condition returning nought for anything not carried, and the test still passed. It now finds an object inside a container and demands the raw field, and the same mutation fails it.
