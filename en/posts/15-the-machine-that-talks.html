The machine that talks

The conversation interpreter now runs the scripts of all 199 characters. The interesting part was not the rules that work, but the three that are wrong and must not be corrected.

The instruction set and the file format were already done. What remained was the thing that runs them: an expression stack, the skipping of untaken branches, jumps, assignments. It felt like mechanical work, and most of it was.

Three rules that must not be tidied

Dividing by zero leaves the dividend. The original prints an error and stores nothing, so the dividend survives on the stack as the answer. Returning zero would look tidier and would be a different game.

Four relational operators compare unsigned, and equality does not. The original casts only the former. So minus one is greater than one, and still equal to itself. Reproduce only one half of that and the result looks like a rounding difference and behaves like a different rule.

The skip does not nest. When a condition is false, the scan forward stops at the first end marker it meets rather than at its own match. A false outer condition therefore stops at the inner conditional's end, and the rest of the outer body runs anyway. 

IF (false)
    "outer body"        <- skipped
    IF (true)
        "inner body"    <- skipped
    ENDIF               <- the skip stops here
    "rest of outer"     <- runs anyway
ENDIF

This is the mechanism that makes character 164's party dismissal branch unreachable, which I wrote about earlier. "Fixing" the skip would bring it to life, and no test would notice.

A fourth, smaller one: the skip steps over the operands of a jump and of the byte and word constants, but not over the four bytes of a script address. I wrote a test that demonstrates the leak happening, because a latent fault that is not tested has not been reproduced, it has been forgotten.

The corpus test found what hand written tests could not

Hand built expressions prove the rules. They do not prove the rules are enough. So I wrote a test that walks all 199 scripts, finds every condition, and evaluates it.

On the first run it failed in exactly one place: character 53, array index 65545. That is the bug I had documented long before without knowing its consequence: a carrying check indexes an array with a text variable where an integer variable was meant.

I had written then that "the weight is read from the wrong place", without knowing how wrong. Now I know. The original keeps an array index in a single byte variable, so 65545 is truncated to its low byte, which is 9. And 9 is exactly the variable number the author meant.

So the read lands on the wrong entry but stays inside the array. That is why the shop has always seemed to work. I updated the bug report: a guess was replaced by a measurement.

A second find from the same run: one condition indexes an array at #9 + #0 - 1, which is minus one before anything has been set. The original then reads leftovers from the previous conversation out of a ten kilobyte buffer, and does not crash. There is nothing to reproduce faithfully there, so I return zero and said why in the code.

The numbers

Once everything worked, I ran the corpus test to the end: 

2347  condition expressions, all evaluable
 172  openings that wait for a question
  26  openings that end the conversation outright
   0  openings that run off the end of their script

The last line says the most. If the operand length of even one instruction were wrong, the walk would drift out of step and start reading text as instructions. Zero out of 199 means it stays with the byte stream the whole way.

What I left throwing

Four things are not implemented: keyword matching and input, printing a text variable, two search instructions, and writing into an array inside the script.

They throw a clear exception rather than being quietly wrong, and the corpus test counts them: one opening out of 199 hits one. That seems to me the right way to leave something unfinished. A silent default would have made it look as though everything was done.
