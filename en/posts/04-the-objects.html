Sixteen thousand objects and one suspicious bit

Finding the flag that separates things lying on the ground from things inside a chest, by elimination.

The terrain is only the floor. Everything a player can see or touch (trees, buildings, doors, barrels, swords, people, monsters) is an object, and there are 16,838 of them in the starting world: 9,098 above ground and 7,740 below.

Each one is eight bytes. The byte that holds the status flags is obvious enough, and so are the blocks of records, each prefixed by a count. The hard part is that the coordinates straddle byte boundaries, and there are several plausible ways to divide them up.

Letting the data choose the layout

My first reading produced dungeon objects with a y coordinate of 576. A dungeon level is 256×256 tiles. That is not a rounding error, that is a wrong answer.

Rather than guess again, I let the dungeons arbitrate. There are exactly five dungeon levels, stored as five blocks. If the bit division is right, then the level field in the records of block n should contain nothing but the value n, and every coordinate should fit inside 256. Only one division of the 24 bits across three bytes satisfies both: 

x    = b1 | ((b2 & 0x03) << 8)        10 bits
y    = (b2 >> 2) | ((b3 & 0x0F) << 6)  10 bits
z    = b3 >> 4                          4 bits

With that layout the five dungeon blocks yield level numbers 1 through 5 exactly, and the surface blocks yield 0 throughout. The data verified the format for me.

The objects that are not anywhere

Not quite. A few hundred records still had impossible coordinates, and they were scattered across every block. Something else was going on.

The explanation is that not every object is on the map. Objects inside a chest, a barrel or a character's pack are stored in the same list as the ones lying on the ground, and their coordinate fields are reused for something else entirely. There has to be a flag that says which is which, and it has to live in the status byte.

Eight candidate bits, and a clean way to test each one. Every surface block corresponds to a single 128×128 super chunk, so if I filter out the objects a given bit marks, the survivors should all fall inside one super chunk. The right bit should make nearly all 64 blocks resolve cleanly; the wrong ones should make no difference at all.

Bit 0x08 marks an object as contained. 1,705 of the 16,838 objects are inside something else. The result is not subtle, which is what makes it trustworthy: every other bit scores identically to doing nothing at all.

Seven that still do not fit

After that filter, seven dungeon records out of 7,740 remain stubbornly out of bounds. All seven carry a different status bit, 0x10.

Seven samples is not enough to build a rule from, so I did not build one. The parser keeps them, a test pins the count at exactly seven so that any change to the parser moves the number and fails, and the finding went into a separate log of anomalies to resolve once I can read the original's own handling of the status byte. Writing a plausible-sounding rule from seven observations is how you get a bug that surfaces forty hours later.

Quantity and quality

The last two bytes of each record were a mystery for a while: clearly two small values, but which was which? The answer came from the original's own code, which packs them into a single 16-bit value with one in the high byte and one in the low byte. That fixes the order , but reading it somewhere is not the same as confirming it, so I cross-checked against the name table from the first post.

FieldWhich object types actually use it
byte 6, high valuesgold coins, gold nuggets, arrows, bolts, bags
byte 7, non-zerobooks, keys, shrines, ship deeds, tombstones, scrolls

Byte 6 runs high on exactly the things you would stack. Byte 7 is non-zero on exactly the things that need telling apart: which book, which key. Quantity and quality, confirmed from two independent directions.

One oddity sits at the top of both lists: an object type called egg, far more common than anything else and using both bytes. Eggs turn out to be the game's creature spawn markers, with the two bytes as parameters. They are invisible, they are everywhere, and they are why the most common object in Britannia is something no player ever sees.
