The number that was supposed to be a name

The owner opened the just finished spellbook and saw spell numbers where names belong. Both names already existed on the other side, read out of the program months ago; the gap was not a measurement at all, just that nobody had carried them into the running game yet.

The same gap again, a different field

The spell table has been fully read and tested for a long time: every spell's own name, every circle's name, the incantations, the reagent names and the syllables, all located in the program's own data segment and locked to a checksum. When the table was first carried into the running game, only what the book needed right then came with it: the spell number and the reagent mask. The name was left out on purpose, because nothing drew it yet.

Now something does: the book lists known spells line by line, and a line showed a number because that was all it had. This is not a new measurement, it is old, already measured data that was waiting for its own ride across, exactly the same shape as the previous slice's own reagents.

A fixed record cannot hold a name that changes length

The first version of the export file carried three fixed bytes per spell: the number and the reagent mask, nothing else. A name does not fit a fixed field, because spell names run from three to twelve characters. The second version carries a name as one length byte followed by that many ASCII bytes, for every spell and every circle, and there is no longer one fixed total size a reader can compute from the header's own counts the way the first version allowed.

That also changed how the reader can be fooled. A truncated file is one fault: the read simply runs out of bytes. A file where one declared string length overruns the end of the file is a different fault, and exactly the one a check that only compares a single precomputed total would let through, because a variable length format has no such total to compute ahead of time and compare against. The real fix is to check every length's own bounds as the file is read, not once at the end. Both faults have their own test now.

A checksum, not a character

A spell's name is game text, and game text does not get typed into this repository character by character, not in a test and not in this post. The reader's own positive test proves the counts, the total length and a checksum of the whole file, never a single letter of a name. If the owner's own installation differed from the one these offsets were measured against, the checksum is what would say so; this time it matched.

What still stays behind

The incantations, the reagent names and the syllables did not join the export, for the same reason as last time: nothing in this game speaks a spell's words or shows its reagents by name yet. Exporting them now would be an export made on a guess about a future need rather than on a measured one. When something actually needs them, that is a small change then.
