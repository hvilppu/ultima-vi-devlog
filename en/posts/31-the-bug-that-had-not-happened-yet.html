The bug that had not happened yet

The object world can change now, so a thing can move from one square to another, into a pack and into a container. But the whole reason for this slice was a bug nothing had committed yet, because nothing had moved yet.

A position is not an identity

Post 28 settled how a container's contents name their container: as a slot within one block, translated into an index over the whole list. It worked, it was measured, and tests held it in place.

It was also right only for as long as nothing moves.

An index is a position in a list. When an object moves and the order changes, every stored container reference names a different object. Not an empty slot either: it names a real object, on some square, of some type. The contents of one chest would be inside somebody else's chest.

So no exception, no crash, nothing a test would catch unless written for it on purpose. Just a wrong answer that looks like data.

The original never meets this

Because it has the two separately. An object number is a slot in a fixed pool, so it is stable, and the order is its own singly linked list, Link[]. A move changes the order and not the identity.

That is an architectural split which 1990 got for free out of its memory limits. We got it for nothing, and what we got was wrong.

The fix is the same split. An id is a position in load order, fixed once and never again. The order is its own list. The export did not change by a single byte, because the file is already in load order.

The chain is a rule, not an implementation detail

I read OBJ_CompareOrder and the two move primitives, and the chain carries three invariants: 

1  map objects in order of y and then x
2  a container is followed immediately by its contents, as a subtree
3  anything new or moved goes in FRONT of what already stands there

The first two I measured from the file. The third is the one that nearly went in backwards.

In front, not behind

I was writing an implementation that re-sorts the chain after every move. A stable sort, which keeps the relative order of objects on one square. Sensible, and simple.

And wrong, because a stable sort puts the arrival behind the residents. I stopped to read what the original does, and OBJ_FindListPos's own comment says it outright: new objects go in front of the objects already on that tile. Its loop confirms it by stopping at the first object whose row is past the target, or whose row matches and whose column is not before it.

The difference is drawing order. A dropped object would have been drawn on the wrong side of whatever is already there, and that would have looked like nothing at all: it would have looked like an object on a square. One comment told the two readings apart.

The file was not in order after all

I wrote the invariant check and it failed on the real data immediately. For a good reason: the file is sorted within each block and not across them. A block is one super chunk, so the row number starts over at every boundary, 69 times.

The original never meets this either, because it holds only the 2x2 areas around the party or one dungeon level, at most 2815 object slots. Its chain covers exactly what is loaded, and so it is in order. We hold all 16838, so the chain has to be sorted across the whole world.

The sort is over roots with their contents, so a subtree stays together, and it is stable, so objects on one square keep the order the file gave them. That is why the renderer sees exactly the same sequence as before, and why 698 tests passed after the change without one of them being touched.

Two things the tests caught me doing

Building the chain dropped loops silently. I build it from the roots down, and two objects inside each other are neither of them a root. They never reached the chain and nothing said so. An existing test asserting that a loop is rejected failed, and it was right. The check is now exact rather than a depth limit: the chain is as long as the number of objects, or something is unreachable.

I wrote the number 13386 by guessing. It is how many of the 15070 pairs are also in order under the wrong reading, column before row. I guessed it by adding the per-block figures in my head, put it in an assertion, and the assertion failed: the real number is 13386 and not what I had written. The same mistake as the weight table's commit message last time, and this time it was caught before it reached anything permanent.

So the wrong reading is right 88.8 per cent of the time. Exactly often enough to look correct and never be questioned.

One inconsistency went away on the way past

Changing a frame, which is what a door opening is, used to write the new frame into the square's own list. The full object list and every other lookup went on saying the old one. The plan had recorded that as an inconsistency and nobody had fixed it.

It is structurally impossible now, not because the method is careful but because there is one copy to change. The lookup buckets are rebuilt on every change, which is one pass over 16838 objects per move. That is a trivial price and it removes the place a stale entry could hide.
