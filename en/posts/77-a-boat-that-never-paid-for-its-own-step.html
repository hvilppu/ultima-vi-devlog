A boat that never paid for its own step

M16's slice A, and it closes a fault of its own making: the previous slice (M14's E1) replaced the fixed five minute step with the real turn scheduler, but a boarded vehicle's own step never charged for itself. The clock now only runs when nobody is eligible to act, and an Avatar that never spends anything is always eligible with a full share. The result: a voyage from one continent to another arrived at the same minute it left.

A character time never touched

The fault was not in a cost calculation, because there was none: U6View.AdvanceVehicle moved the vehicle on the map and then called the turn scheduler directly, spending nothing from anybody. U6TurnScheduler.Advance only grants a new minute and ticks the clock inside its own while(!TrySelect) loop; with the Avatar's points never falling to zero, that condition is false from the very first call onward, and the loop's body never once ran. The walking party never had this problem, because Follow already spends the Avatar's own SubTerrainMov; the vehicle was the one case left that never got tired.

Four branches, and the order is the measurement

npctrack.c's own cost branch tests the controlled actor's type in an order where the first condition can fall through: a ship pays the wind table only while the wind is blowing; a skiff pays the current table, its flow direction read off the departure square's own tile number when that square is one of the eight current tiles (8 to 15, the direction being the tile number minus eight) and its own heading otherwise; a raft or an inflated balloon pay a flat five; and everything else, a becalmed ship included, falls through to the plain terrain cost, plus 5 on a diagonal. The fourth branch is the one a port easily misses: a becalmed ship does not index the wind table at all, because the test is on the wind blowing, not on the actor's type. The current tiles were measured against the owner's own export as a check: all eight are wet, impassable to a walker and carry no object, so the plain terrain cost there is exactly Base, 5.

The ship's table does not look like you would expect

The skiff's own table is cheapest with the current and dearest against it, the intuitive shape. The ship's own table is not that shape: its dearest entry is index zero, straight into the wind, and its cheapest are two and six, the wind from the side; running with the wind (index four) costs five, not the least. Both tables turned up in the owner's own GAME.EXE as one sixteen byte run, occurring exactly once, in the reverse order scoring zero hits, with the very next byte being the raft's own drift table's first row exactly as the decompilation claims. A port that "corrected" the ship's table to look like the skiff's would have traded a measurement for a guess, and the test pins all eight values individually for exactly that reason.

A regression that cannot run through the view itself

U6View is a MonoBehaviour and cannot run outside the editor, so the regression could not be reproduced by calling AdvanceVehicle directly. It was reproduced at the engine's own boundary instead: a test drives U6TurnScheduler.Advance repeatedly while spending nothing, and proves the clock stays exactly where it started, which is precisely what the unfixed view did. The same test spending the real cost passes; a temporary experiment that removed the spend from the loop knocked it back down at exactly that line. The test was written and proven to fail before the fix, not after.

What this does not do yet

The raft's own drift table (RaftDriftDir) sits right beside the two cost tables in the file, but it is a different behaviour: a raft drifts with the wind and the current whether or not the player steps, and it is not needed to close the clock. WindDir's own random change over time (UpdateWind, a one in sixty four chance on every call to PassTime) is not modelled in this engine at all; the wind stays at whatever the save file set it to until the fan item turns it.
