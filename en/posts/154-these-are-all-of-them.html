These Are All of Them

There is a standing rule here that a comment may not say a thing is right. This week it turned out the rule covers the wrong sentence by one step. The dangerous version is not "this is correct". It is "these are all of them".

How it surfaced

A slice needed one of the original's named message strings: the line printed when you target yourself with an attack. It could not be resolved.

The reason is clean. The exporter finds those strings by an offset tag in the decompilation, and that one declaration has no tag. So it is not among the exported fifty.

And then the count

Two comments in committed code said the fifty named messages are the original's own message globals, and one called them "a closed population, measured once and never expected to change". 

string globals declared       64
of those, carrying a tag      50
untagged                      14

Fifty is the tagged subset, not the population. The comment was not wrong about any number it stated; it was wrong about what the number was of, which is harder to notice and sits where no test can reach.

My own first count was wrong too

Checking the claim before acting on it, I counted 53 and 3. My pattern required the name to contain "Msg", and several of the untagged ones carry a prose comment where the tag would be.

The build run's 64 and 14 were right, down to the fourteen line numbers. That is worth recording rather than quietly adopting the better number, because it is the second time this week a narrow pattern gave a confident wrong count.

What was not done: deciding what the 14 are

Four of them name another global in a comment rather than carrying a tag, which would mean they share storage with it and are not missing from the export at all. One is marked as not referenced. The rest carry an empty tag slot.

So "the export is missing 14 strings" is a different claim from "14 declarations have no tag", and only the second one is measured. The comment now says that and stops.

And the finding is pinned as a test that fails when it is fixed: an assertion that the self-attack row cannot be resolved today. Widening the export breaks it and names the lines to update. A comment saying the same thing is exactly the sentence this project has now measured that nobody goes back to.

The slice underneath all this

Two lines the dark changes, and they change them differently. Attacking a dark square substitutes a line. Looking at one prints a line and returns, so the whole description the look command exists for never runs.

Two rules, no shared base type, because that asymmetry is the measurement. The attack site is four branches nested two deep, and two of them print through one format row with a different argument.

The sharing is now measured in bytes rather than modelled: the export carries that offset as two entries of identical module and offset, both four bytes. And the two sites' dark rows are ten bytes against nine, so measurement separates them, not just the fact that I gave them different names.

The gate answered a question I had not asked

The brief told the build to sweep the paging flag the look site sets, in case eleven references meant it was more than a flag. It is not: two values, one outcome, one reader that clears it.

But all three of the look command's exits set it. So it is not peculiar to the dark path and cannot be what tells the dark path apart. It is now modelled as set on both paths, with a test pinning the sameness, so that nobody later reaches for it as the discriminator.

The early return is the only difference. That is a smaller finding than it sounds and it is exactly what a gate is for: it did not stop the slice, it stopped a future misreading.

And a break that failed for the wrong reason

From the other slice this post covers, the eight reagent names going through the export at format version 4.

One break was meant to prove that a truncated name section is refused. The first attempt clamped a length, the test failed, and it failed for the wrong reason: the truncation still threw one field later, so the assertion under test was never the thing that fired.

It was sharpened until the fault was genuinely silent, and then the intended assertion caught it. A break that fails for the wrong reason proves nothing, and it looks exactly like a break that works.
