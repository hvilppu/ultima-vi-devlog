A Third Project Because Two Must Not Know Each Other

The last post left wiring the live world into the block to superchunk link open. That is done now, but the road there ran through an unexpected place: a wall between two already existing projects, put up on purpose rather than by accident.

The engine and the file format must not know each other

The game's live state (U6Engine) and the save file's own byte layout (U6Formats) reference each other nowhere. That is not an oversight: Unity sees the first and not the second, and if the second referenced the first, that boundary would fail quietly. Turning a live world into save bytes needs both at once, though. The answer was a third, small project, Tools/U6GameSave, which references both directly and never has to sit inside Unity. Neither rule breaks, because neither existing project changes at all.

An area comes from the root, not from the object itself

A map object knows its own area straight from its own position. A contained object knows nothing, but its container does, and the object chain's own invariant, a container always before its contents, guarantees the container's area is already settled by the time its contents are reached. A carried object knows nothing either, but the character carrying it does, now that U6Vehicles.TryGetSavedPosition can also answer for one who is aboard a vehicle. Three cases, one walk down the chain, and not one special case that was not already measured before this.

The position-based formula cross-checked against every real on-map object in the game

A new formula, area straight from x and y, needed proving on an independent path. Every object in a given block of the shipped initial state sits, by construction, inside that block's own 128 by 128 tile area. When every single on-map object's own position gave exactly the area the already-measured, stream-index based formula already gave, two independent paths landed on the same answer for every on-map object the shipped game has.

Not byte for byte, and that is the right target

A block's own order here comes from the object chain, not from the file's own unmeasured write order, so the output is not byte for byte identical to the shipped file. That is not a gap: the last post showed the original itself never reproduces its own leftover byte twice, so chasing one historical file's exact order would not have been a goal worth having either. What is proved instead is content: every area's own record count matches the real, untouched save's own count, and four kinds of live change, a moved object, a new item in a container, something carried, something carried aboard a vehicle, land in the right file with the right local reference.
