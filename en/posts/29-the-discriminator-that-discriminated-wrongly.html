The discriminator that discriminated wrongly

Measuring the weight table was a one-line job in the plan: the table's position is known, so export it. It turned into three findings, and the first is that my first proof was wrong.

The table existed, and was still missing

The code claimed in two places that the weight table had never been exported. That was not quite true: the table was read and its weights were already in the type descriptions. But the runtime data did not have it, because tileflags.bin holds only the three tables indexed by tile. So the claim was right about what it meant and wrong about how it sounded.

The original loads TILEFLAG as four consecutive tables, and the weights are the third, so the position follows from the load order. Proving it was still necessary, because the other three tables are one flag byte per tile, and indexing any of them by object type gives small integers that look like weights.

The first discriminator

I reasoned: anything somebody carries must be liftable, so its weight cannot be zero or immovable. I counted it for all seven windows of the file: 

window    held objects with a weight
0x1000    1393 / 1767     (chosen)
0x1800    1701 / 1767     (the secondary flag table)

A flag table scored better than the weight table. And even under the chosen window, 294 held objects weighed nothing and 80 were marked immovable. The assumption was wrong, and it could have ended up as a test that protects the wrong table.

I looked at what those types are. Twenty types, two of them named charge and effect, which the original's own code names separately as internal types. Eighteen have no name. None is something a person carries. So "everything held is liftable" is not true, and it is now visible in a test so that nobody tries it a third time.

The discriminator that worked

The original's code gives the number 255 a meaning of its own: immovable, turned into ten thousand. The table it describes is the one that contains 255 at all: 

window    255 markers    overloaded at the start
0x0000     0             16
0x0400     0              0
0x0800     0              0
0x0C00     0              6
0x1000    18              0     (chosen)
0x1400     0             11
0x1800     0              9

Only the chosen window holds 255, and nine of its 18 types have names: crystal ball, harpsichord, harp, open barrel, open crate, milk bottle, anvil, bellows and sundial. The second discriminator is the carrying limit: the 34 characters who carry anything at the start fit their limit only under the chosen table and the two windows that the 255 marker rules out. The two discriminators remove different sets, and between them they leave one.

I broke the choice on purpose to watch the tests fail. Moving to 0x1800 failed five tests and moving to 0x0400 four. In the second the overload test did not fail, which is exactly what the table above predicts: the 255 marker removes it.

Reading the handler found my own mistake

When I read the handler for the CanCarry instruction I saw that it stops at nought. My own U6Carrying.RoomRemaining let the room go negative, and a test asserted it. The reasoning sounded sensible: an overloaded character should read as worse than a full one. It was written from the surrounding code and not from the handler, and the handler says otherwise: a full character and an overloaded one answer the same.

This is the same fault as before: a plausible test that confirms its own assumption. I fixed the code and turned the test around. Then I broke it once more by removing the clamp, and four tests failed.

The measure moved by one, not two

                         before   after
corpus runs to the end    190      191   / 196
CanCarry stops              2        0
GiveObject stops            0        1

I expected two. CanCarry stopped two conversations, and when the table was handed in one of them ran to the end. The other got further and now stops where it asks to give somebody something, which nothing answers yet. It had only been hiding behind the first. I could have written 192 and it should have felt right.

Three rules on top of the table

Besides the table the original does three things, each easy to get wrong when simplified: gold and the reagents are weighed per ten, a lit torch counts as one, and exactly 255 is immovable. The last is tested on the product and not the entry, so a pile whose count times its entry is 255 becomes unliftable, and two things marked 255 weigh 510. That is a fault in the original, and no shipped pile reaches it. It is reproduced and recorded.
