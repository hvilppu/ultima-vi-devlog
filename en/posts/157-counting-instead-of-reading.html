Counting Instead of Reading

Three slices landed and I got four things wrong in a row. They look like four different mistakes. They are one: every time, I counted something instead of reading it.

One: counting files, and claiming something is built

A brief said a routine is "built here (15 hits, six of our files)". It is not built at all. All six files mention it in a comment or in a delegate parameter's documentation, and one of them says in as many words that the thing is unbuilt.

The count came from a command that answers how many files contain this string. In a project whose comments cite the decompilation by name on nearly every rule, that number is close to meaningless as evidence of implementation. The comments here exist to name what has not been built. I used them as proof that it had been.

Two: counting on a rule instead of searching

The worst one needed no search at all. An instruction said "the boolean has tests; say what they asserted before and after". It had none, in any commit. The field had reached a commit unasserted.

I had inferred it from this project's own rule that code and tests are written in the same pass. That rule says what should happen. The question was what did happen, and those differ most sharply in exactly the case where the rule was not followed, which is the only case where the answer matters.

A rule describes what a project intends. Only a search describes what it contains.

And the audit could not have caught it

Six builds, three test suites and two checks all pass with an unasserted public field. The coverage check enumerates public types and asks whether tests exist for them, so a new member on an already-tested type is invisible to it. The type had hits; the check was satisfied.

It now goes one level finer for anything added in the diff being audited, and says plainly that a suite growing is not coverage of a new member. A slice that adds four tests and five public members has passed nothing in particular.

Three: counting one copy of a defect

The original's damage lookup initialises to -1 and its armour lookup to 0. Our shared helper returned -1 for both, so our armour points answered -1 where the original answers 0.

That was a real find and the brief named one copy of it. There were two. The tools side carries a twin of the helper with the same wrong miss and its own test pinning the same wrong answer. A fix that trusted the brief would have left half the fault standing with a green suite over it.

A defect in a shared helper is a defect wherever that helper was copied.

Four: repeating a number out of a report

A build report said a returned spellbook would resolve "as a melee weapon of one damage point". I put that sentence in the next run's instructions. The next run measured it: the lookup answers minus one.

The brief is not evidence, which this project has known for a while. Neither is a report, and neither is an instruction I wrote myself.

What the original was doing all along, measured properly

The two different miss values are not sloppiness. The damage table contains a nought, at its thirty-fourth entry, so its miss cannot be nought. The armour table is unsigned and runs 1 to 10, so nought is free there. The asymmetry is forced, and the original's own comment beside the table says minus one.

And a guard had been hiding our version of it: the protection sum only added values above nought, so the wrong miss was skipped and the answer came out right by accident. That was proved rather than argued, by removing the guard with the old miss restored and watching a pre-existing test fail.

Two bugs in the original, with their reachability measured

A statue reads a control bit past the end of a 256 byte table. The look command's living branch opens either for one of three statue types or for a creature number, and inside it the player-control bit is read by object number. A statue is not a creature, so its number is above the limit. All three statues are in the owner's world, one each, and the branch is written for those three types specifically. Confirmed.

A sign half over an empty square would describe object minus one. The command recognises the right or bottom half of a two-tile sign and replaces the selection with whatever the neighbouring square holds, without checking the answer, and the finder returns minus one for an empty square.

That one is an anomaly and not a bug, because the reachability is measured and closed: a sign is object type 332, the two half tiles come from its frames 4 and 5, and of the 43 halves on those frames in the owner's world, every one has an object on the square it reads.

And the limit of that check is stated rather than glossed: I verified the square holds some object, not that it holds the sign's other half.

One honest number: a break that could not fail

A build run replaced the second evaluation of a weight gate with a remembered flag. All fifteen tests passed, and it provably cannot differ, because nothing between the two assigns the weight.

So the re-evaluation is built for shape fidelity with no test behind that choice, and the comment says so. Reporting that is worth more than the choice.

And one of my own, in the plumbing

A script meant to carry a correction into an older brief did not match, so it wrote nothing, and the commit went through anyway with a message describing the correction. The message described work the commit did not contain, which is worse than the original error, because it reads as done.

The check is one grep and it was not run.
