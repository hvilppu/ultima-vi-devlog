Not Even the Original Gets the Same Byte Twice

The last post left two things open: which of 69 files any given object belongs to once the world is live, and one real save from the actual game. Both are resolved this round, but finding the save first exposed an entirely different problem, and the save itself then exposed something that changes M18's own yardstick.

The save was never going anywhere, because it was never going into this repo

This project's own test folder, Original Ultima 6/SAVEGAME/, stayed empty after saving no matter what happened in game. The cause was the DOSBox launch config: it mounts C twice, the second time with an overlay, specifically so the game can never touch the files underneath. The owner's actual playable copy lived in a completely different folder on disk, and this repo's own copy had never been a runnable game at all, only export material. The fix was simple: the launch shortcut's target and working directory now point at the repo's own DOSBOX folder, so the config's relative mounts find the repo's own side instead. From here on, a save lands in the repo's own, gitignored cloud_saves/SAVEGAME/.

One real save answered three questions at once

A real CTRL+S produced five files: the whole OBJLIST and four changed blocks, the other 65 untouched. Three things settled in one run. The saved OBJLIST is 7283 bytes, not 7539, exactly the predicted number. The contained object's uninitialized third byte (post 45) behaves on played data exactly as it did on the shipped data: constant or two values per block. And the incremental save claim held up structurally, not just by inference from what was read: the 65 untouched blocks were simply missing from the overlay, which under DOSBox's own overlay semantics means untouched, full stop.

A second save broke the yardstick itself

A second real save was taken from the same play session, the same 944-record block, whose record count had not changed at all. The first time, the third byte took two values. The second time, three. Same data, two saves, a different leftover. This is not a mistake of ours and not a gap in the measurement: it proves directly that the original itself does not produce the same byte twice from the same state, because the byte is not game state at all, only whatever happened to be on the stack at that moment. The consequence lands squarely on M18's own yardstick: "byte for byte" can never cover this one byte, by any writer, and chasing it is not a goal worth having.

The block to superchunk link

Flattening the world into one list on load threw away the block boundaries, so nothing knew which of 69 files an object belonged back in. Block lengths now survive loading, and two new splitters hand the initial state back into the 64+5 blocks it was read from. A small class of its own carries the measured 2x2 grouping formula that used to live only inside one test. Splitting and writing back out reproduces all 69 real files byte for byte, on a path entirely independent of the direct read-and-write test that already covered this.

Two steps of nine, and one suspicion that turned out wrong

Of the save's nine live-state steps, four turned out unnecessary: 1990s memory limits, not observable rules, the same line this project already drew when it chose not to recycle object numbers. One of them, deleting far away marked objects on save, needed its own measurement: both of its loops only ever touch the original's own windowed load, never the whole world, so a global version here would be a new rule rather than an imitation. The quest flag's own save step was built as a tested primitive of its own. And the party's position while aboard a vehicle during a save: an initial worry that the vehicle's own position might differ from the leader's square turned out wrong on reading the original's own boarding function, which does exactly what this project already does: the leader moves onto the vehicle's square, not the other way round.
