The Test That Could Not Fail

This stretch found four tests and checks that had no way to fail, and each was found a different way. One was blind at a single coincidental parameter value. One was blind at a fixture whose name happened to be capitalised already. One asserted a sound's count and not its identity. One was parameterised by the very constant it was meant to check. And one break proved more than it was asked to.

The first, which taught this stretch to be careful

Thirteen entries from the hundred-rule list were answered one by one. The screen shake was wired the same way the dissolve already is: the rule answers steps, the view turns steps into time with a named constant of its own, and no test pins that constant. That was verified by changing it and watching every rule test stay green.

The best thing in that report is not what was built, it is a test that stayed green under a break and should not have comforted anyone. Breaking the offset formula failed five assertions in the rule's own tests and left the new playback tests passing, because they compare playback against an independently computed call of the same broken rule. They prove faithful consumption and not correct numbers, and the run said so rather than counting them as cover.

Four blind tests, found four different ways

The first was blind at a single coincidental parameter value. Merging two of three missile-shaped arms passed all forty five tests, because the test's own parameter was 125, the single point where both formulas reach zero. The run found the coincidence itself, added a second point further away, and the break then failed exactly as predicted.

The second was blind at a fixture whose name happened to be capitalised already. A test resolves a name that is already capital, so a break in the capitalise control is invisible to it. The run reported this as it stood rather than quietly swapping the fixture.

The third asserted a sound's count and not its identity, and was found by a run that went looking on purpose, the first time this stretch. The assertion said a gremlin plays one sound with no draws from the random generator, and it passed when given the corpser's sound instead, because both are zero-draw sounds. It now pins the sound's own content rather than only its shape.

The fourth was parameterised by the very constant it was meant to check, and was found only by running the break, not by reasoning about it. An instrument-length test read its expected value directly off the constant it was supposed to verify, so shortening that constant failed nothing there at all. A positive pass over all twelve song files did not fail either, because a wrong alignment does not throw, it reads the wrong bytes as commands, which is exactly the silently wrong case this project's rules exist to catch. What caught it was the truncation test, which stopped refusing. The replacement hardcodes the number and fails on the exact byte.

A break that proved more than it was asked to

Changing a constant by five orders of magnitude failed nothing, and the reason is structural rather than lucky: the view is not compiled into the engine's test assembly at all, so no rule test could ever see that constant. That is the strongest form of proof a decision could ask for, and a different thing entirely from a test that simply happened not to fail.

What no test can ever see

The four blind tests share one side: they were tests, written wrong. The other side has four places where no test, written right or wrong, could ever have seen what broke, because the composition lives in the Unity assembly, which has no headless path at all.

The owner's first capture showed a hit line full of raw object numbers. A second showed the same line naming the decompilation's own identifiers. A third invented sentence sat beside it, untouched by the two earlier removals, because those worked phrase by phrase and this frame was not a phrase. The fourth time in this project, the owner's own machine was the instrument that caught it.

The sound side added three more, none of them a code fault in this project. The speaker asked Unity for its sample rate inside the audio thread's own callback, which throws because that property is allowed only on the main thread, and nothing here could have caught it before the editor did. The source was blended towards three dimensional sound and its priority sat three steps off Unity's lowest, neither of them set by this project, and the component had left everything else to whatever the scene serialised. And the queue advanced once per rendered frame by that frame's own elapsed time, so a whole effect was consumed inside a single update before the audio callback ever ran, which is exactly the kind of timing a headless run does not model.

Two sides of the same coin

The four blind tests and the four capture-caught defects are not two different phenomena. They are the same question asked two different ways. A blind test asks what this test truly asserts, and sometimes answers wrong about what it claims to be. A capture asks what this project can see at all, and sometimes answers nothing. Neither is fixed by more code; both are fixed by someone asking which question is being asked right now.

This project's own rule says a test or a check must never be the kind whose assertion could not have failed. This stretch showed that checking that sometimes means running the break instead of reasoning about it, and sometimes means asking the owner for a capture, because nothing here can look.
