The button that never selects

The previous slice built what the spellbook decides. This one builds what a key press or a click does to it, and draws the page afterward. The split stayed the same: every rule into the engine, the Unity side as thin as it can honestly be.

Turning the page is choosing a spell, not editing an offset

In the original, SpellbookFirst is its own independent state, and four command handlers edit it directly: plus eight, minus eight, or a whole fresh walk across circles. In this project the page's own starting point is entirely a function of the selected spell, so turning the page needs no second piece of state at all: it is enough to find the spell that becomes the new page's own first line and run it through the very same function every other selection already goes through. The two routes always agree, because they are the same rule read twice.

A button and a key are not the same thing

A close reading turned up a distinction that would not have been guessed ahead of time: the four navigation buttons reach the command handlers straight from a mouse click, and never reselect a spell, the page simply changes underneath whichever one happened to be selected. The direction keys, by contrast, always select the new page's own first line, because the key's own path carries a flag the click never sets. The difference is measured, not invented: the original's own SpellbookPageChanged only checks that flag where SpellbookKeyNav is the one that ever sets it. The test checks both directions on purpose, because either direction alone would have looked perfectly sensible.

The previous circle button's pinned fault (slice F12, left unfixed then too) turned out to reach further than the displayed number: pressing the button for real lands on the wrong circle, not only shows the wrong one as its own value. The same test that measured the display fault now measures the navigation fault too.

The Unity side, as thin as it gets

C opens the book, the arrows navigate, Escape closes it: three named, unmeasured decisions, the same shape as the attack command's own targeting before it. The mouse is left unbuilt, for the same reason as then: this view has no pointer. The drawing is a plain text box, not the original's own parchment picture, because this project has no status panel in the shape the original draws into; character 0x1A is written exactly as measured, and whether it shows as an arrow or as nothing at all is a question only the owner's own eye can answer.

What puts a spellbook into a party member's hand was not traced in either slice, so the book slots here stay permanently empty. The key mapping is demonstrably working, but the book that C opens is always empty until equipping gets its own, measured slice.
