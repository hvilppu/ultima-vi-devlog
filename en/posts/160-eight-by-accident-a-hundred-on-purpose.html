Eight by Accident, a Hundred on Purpose

The previous post was about one rule: measured, built, tested, and nothing showed on the screen. This one is its sequel. The same shape turned up eight times in this stretch, every time by accident, every time while looking for something else. So the question was finally asked once, for everything: of 927 public entry points, about a hundred have no caller.

Eight, each found on the way to something else

Rest and camp. The look command's own spellbook arm. The spellbook's own print script. The balloon plans. Two spell families behind a placeholder. The mass family's write layer. The attack's own target-naming rule. Every time the code was already right, tested against its own logic, and nothing in the running game ever called it.

Several of these already had a document on record saying exactly that: built, but unwired. Nobody had read that document. That alone was reason enough to ask the question once across the whole tree instead of waiting for a ninth accident.

No entry in the third group lacked its citation, and that was exactly the thing worth checking: one that did would really have been the first group in disguise. The eight found by accident were samples of a hundred.

And the sweep was wrong in both directions at once

The number came out of three narrowing passes. Exact, named calls across the whole tree, never reading the tests: 144 unreached of 927. Loosened to same-file calls sharing a method name, including expression-bodied one-liners that a naive line-skip hides: ten were rescued, 134 left. And a third pass over the 35 names shared by two or more types, read by hand to resolve the real receiver: fifteen false flags corrected, including two shapes a regular pattern cannot see at all, a receiver typed as an interface and a receiver read as a property. Four boilerplate overrides and two parse artifacts were then dropped, leaving 112.

The sweep named its own blind spot: the search is textual and not a call graph, so a method reached only through a delegate stored somewhere could still be hiding in the hundred. The second, and more important one: public fields and constants read as data sit outside the search entirely. That is exactly the shape this project's own scar already has, a value nobody reads rather than a method nobody calls.

And a third, which the sweep did not name, turned up the first time the list was actually used: Tools/ was never searched. The sweep walked the engine, the Unity assembly and the editor folder. U6Vehicles.TryGetSavedPosition sat on the list of a hundred, and it has two real production callers in Tools/U6GameSave/, which were checked.

So the hundred is wrong in both directions at once: a floor, because data-only members were never asked about, and an overcount, because callers outside the searched scope were counted as missing. This is the same scope lesson this project keeps relearning: a search's bound is part of its answer, and an unstated bound reads as no bound at all. The sweep stated two blind spots and had three.

Nine blocked, two deliberate

Six of the nine blocked entries share one real cause: SetIsOnQuest, SetKarma, the conversation flag loader, two default-command calls and one quest value load all wait on loading a saved game, and this project only ever loads fresh game data, never a save. One gap wearing six names, and seeing it as one is worth more than counting it as six. The remaining two blocked entries each need either a creature generator reordered first or a command that exists nowhere in the tree.

The two deliberately unreached: one is the original's own dead code, reproduced faithfully; the other is used by test support on purpose.

What else this stretch measured

A format was read out of the wrong bytes in two files, and the symptom was already written into both files' own comments as an observation about the file, not a reason to look again. The very comment that noticed the symptom is what stopped anyone from rechecking it.

Two places where the original prints nothing and this project printed a line. Inventing output where the original is silent is a worse fault than paraphrasing one, because nothing about it reads as a placeholder.

The leaked-text check learned to read comments and found 38 real quotations it could never have seen before. The miss was reproduced on purpose first, before anything was fixed: a fragment was put into a doc comment, the check ran, and it reported clean while counting that file as scanned.

Two defects where one was hiding the other. A black conversation panel was covering a party list that should never have been drawn at all. Fixing the first did not cause the second, it revealed it. The owner found both by playing.

Three of my own errors, recorded because they teach something: a sweep that named two call sites of three; a claim about repeated pairs read off the rows instead of the pairs themselves; and a report carried forward into an instruction as a diagnosis when it was only a description. The last one made a build run stop and change nothing, correctly.

What the game can do now

Water moves and fire burns. Characters animate. All ten command icons do something real on a click. Look, get, drop, talk, use, move and rest are behind keys. Looking at a thing says what it is. Field spells write to the world. The map window dissolves into view.

What this list is not

It is not a work order. A rule with no caller is not automatically a defect, and the nine blocked and two deliberate entries prove that category really exists. Each of the hundred needs the same question asked, and the answer will sometimes be a named gap. It is not complete and it is not exact: the count moves as entries are checked. The order of magnitude is the result, not the digit.
