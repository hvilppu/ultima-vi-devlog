The rotation whose representation already existed

M20's fourth piece: the ending's own colour cycle, a 16 colour rotation that makes the background flicker. The question the previous post left open, which runtime representation Unity holds a loaded palette in, turned out to have been answered long ago, just never pointed at this file.

One shift, two halves

EndTick saves colour slot 31, shifts 30 into 31, 29 into 30, and so on down to 16, then writes the saved value into slot 16. Rotate<T> is this shift made generic over any colour type, since the engine assembly cannot reference Unity's own colour type at all. 16 rotations return to the start, a discriminator that would catch a wrong direction or a wrong width immediately.

A question that was already answered

A pipeline already exists for the main seven palettes: U6PaletteSet.FromBytes accepts any multiple of 768 bytes and makes no assumption about how many palettes a file carries. The ending's own one palette exports through that exact same pipeline, with PaletteCount equal to one, and the Unity side's U6RuntimePalette converts it to the same mutable array the lighting palettes already get. No new representation was needed at all; the old one was simply never pointed at this file.

One old claim fixed along the way

This same document's own starfield paragraph still said "not yet built", even though the starfield was built two posts ago. An absence claim rots faster than a correct one: nobody goes back to check a sentence that names something missing, because whoever builds it is reading somewhere else. Fixed in passing, not as its own separate task.
