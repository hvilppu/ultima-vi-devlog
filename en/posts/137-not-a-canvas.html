Not a Canvas

The owner asked whether the UI should move to a Unity Canvas. The answer is no, but the answer is not the interesting part: working it out showed that the arrangement this project had drifted into was the divergence, and the one I proposed is the original's own structure.

What it had drifted into

`U6View.cs` had grown to 6754 lines and drew with four separate textures blitted into four placed rectangles: the map, the status panel, the conversation's equipment, the message area. Each slice had added one. The layering was Unity's call order, and the code's own comments were already apologising for it: "this fixes an order rather than leaving one to chance".

One bill had already been paid. The previous slice could not reproduce the original's rule for two routines sharing one screen region, and recorded the gap as a choice. It was not a choice. Separate textures cannot express it. It was an architectural constraint wearing a decision's clothes, and those are the expensive kind to unpick later.

What the original actually does

The graphics driver has two write targets, and a flag picks between them on every drawing call: 

screen         stride 320    almost everything writes straight here
work buffer    stride 176    the map and the sky bar compose here

Three macros split exactly along that line: one writes to the screen, one to the work buffer, and a third copies the work buffer to the screen. The fill picks its row step from the same flag.

So one composed index buffer plus one composition buffer is not an architectural preference. It is the measured structure. And this project already carried the work buffer under another name, the geometry was measured, and every panel already produced palette indices. All that was missing was the screen they should have been writing into.

Three sources that have not seen each other, and the same 176

My brief admitted the work buffer's height was not measured. The structure's own padding field gives it: the buffer is padded to 30976 bytes, which at a stride of 176 is exactly 176 rows, and 176 by 176 is the map window's own composition size.

That turned into a discriminator for the stride itself: 30976 divides exactly by 176 and does not divide by 320 (30976 / 320 = 96.8, not a whole number of rows). So the stride separates from the buffer's own size, not only from the driver's arithmetic.

And the third source was already sitting in this project: the tile pixel-block encoding advances 176 pixels per row, measured and written down years earlier. Nobody had connected it to the screen's structure. Three sources, one number.

The copy does not copy what it is given

The copy that moves the work buffer to the screen rounds its edges to whole words: the left edge down to even, the right edge up to odd. So an odd left edge drags in the pixel beside it, and an even right edge drags in the one past it.

An aligned rectangle copies exactly, and that is precisely why a test of only that case looks like a test and proves nothing. All three directions are asserted, and all three were broken on purpose: the odd left edge failed, the even right edge failed, and the aligned case passed exactly as predicted.

This is not an invisible refactor, and the building session said so itself

The map's own pixels are unchanged, tested bit for bit. Two things did change: the status panel region is black now when nothing has asked for it, and so is every border pixel no routine has ever drawn, as part of the one blit.

Palette index 0 is measured black. Neither colour is the original's: it has an ornate border there and a default party list in the panel, and neither is built here. Before, those places showed Unity's own background, which was no more correct, only less noticeable.

The difference is that the gap shows as a gap now. That is a better state than a gap the engine's background hides, and it points straight at the next piece of work.

Where a Canvas would be right

Anything that is not the original's UI: a settings screen, a scaling option, our own save browser, a debug panel. None of those has measured pixel positions and all of them benefit from layout. They come in a later part of the project and will sit on top of that single blit.

For the game screen a Canvas would be wrong for two reasons. Every position here is a measured integer on a fixed 320 by 200 grid, so anchoring and layout would be fighting the measurements. And the decisions would move into scene and prefab data, which is the one place this project cannot test without the editor, straight against the rule the rest of its discipline rests on.

One thing became expressible without being decided

The original keeps one view state and one screen, so "whichever was asked most recently wins" is a measurable rule. The three steps that draw into the same rectangle are now named.

The rule itself is still unmeasured, and no guess was written in just because the building could now hold one. Writing a guess into a better building is the same mistake in a better place.

Up next
