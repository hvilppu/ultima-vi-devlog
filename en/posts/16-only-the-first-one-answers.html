Only the first one answers

Keyword matching is done. The corpus test found three things, and the worst of them was mine.

The matching rule is short. A keyword answers if it is the beginning of any word of the input, over the keyword's whole length, ignoring case. You could write that in one line and test it once. That would be a mistake, because the rule is short but it has six edges.

Four letters is a story, not a rule

It is often said about this game that the engine truncates keywords to four letters. It does not. The scripts are simply written with four letter keywords, 3002 of the 4563 shipped ones, and a story about the engine grew out of that.

The difference is measurable and now pinned in both directions. The keyword heal answers the word "healer", because the comparison runs for the keyword's length. The keyword healer does not answer the word "heal", because nothing shortens it. If the engine truncated, both would answer.

Three edge cases written the way they are computed

A default answer is the keyword *, and the original checks only its first character. The keyword *sword would therefore answer anything. No data would show the difference: all 237 default answers are a bare star. I still wrote the rule the way the original computes it, because a keyword is data, and data can change.

For the same reason an empty keyword answers any word: a comparison over zero characters succeeds before it looks at one. And case is folded only for A to Z, because the original's tolower leaves everything else alone in the code page the game runs in.

Pressing return on its own ends the conversation, and how that works pleased me. An empty line is replaced by the word "bye" before any comparison. Return is not handled as a command anywhere; it is simply turned into the word almost every character has a keyword for. Eleven characters do not, and for those return falls through to the default answer.

A wildcard that matches the gap between words

The character ? is a wildcard. The comparison walks the keyword, not the word, and never checks that the word is long enough. With an ordinary character that is harmless, because a word's terminator cannot equal a keyword character. A wildcard matches the terminator as happily as a letter. 

keyword  "a?b"
input    "a b"    -> matches

The original holds the whole input as one buffer with its spaces overwritten by terminators, so the comparison carries on into the next word. Not one of the 4563 keywords contains a wildcard, so the game never shows this. I reproduced it anyway, because the rule is in the engine.

Three skips, three different rules

I wrote earlier about the skip that does not nest. There are three of them, and they differ. 

branch              steps over jump, byte, word     not an address
unmatched answer    steps over jump, byte, word     not an address
answered list       steps over                      nothing at all

The third reads bytes until it reads the end of the answers and steps over no operands at all. An operand byte that happens to hold that value therefore ends the skip in the middle of an instruction. Each has its own test, and I checked them by tidying the skips into correctness on purpose: exactly three tests failed, and nothing else. Each test pins its own fault rather than something else by accident.

An unanswered question walks into the data table

The unmatched skip backs up one byte for a keyword list and for a script mark, but not for the end of the answers. In the first two cases that is right. In the third, the run carries straight on into whatever follows the answers, and scripts keep their word tables there.

The protection against that is the * default answer, but two characters have none behind their last question. For character 185 the table's first word is 0x0080, whose low byte is in the instruction range without having a meaning, and the player sees "Unknown command." in the middle of a conversation. For character 58 the run leaves the script entirely.

My own fault was the worst of the three

The corpus test runs all 3089 keyword lists twice, once with input that matches and once with input that cannot. On the first run it failed in dozens of places.

The cause was a resume position one byte out. When an array is indexed, the index expression eats the separator it ends on, and the assignment still needs that separator. The original therefore hands back a position one byte earlier, but only for a word array. Not for a string array, because there the caller reads characters next rather than a separator.

One byte, and only in the indexed form. My hand written tests had never reached that form. The corpus test reached it dozens of times immediately.

A second find from the same run: an unknown instruction does not stop the conversation. Bytes 0x80 to 0x9F are instructions by the only rule there is, that anything from 0x80 up is one, and not one of them has a meaning. The original prints "Unknown command." and carries on with the next byte. My interpreter threw, which would have stopped the conversation where the original keeps going.

The numbers

3089  keyword lists
4563  keywords, of which 237 a bare *
   0  keywords containing a wildcard
3057  matching input answered, out of 3057
2525  non matching answered anyway, through the * defaults
   2  runs leaving the script
  89  answers reaching an unimplemented instruction

The line "3057 out of 3057" is the one that pins the matcher. If matching stopped working these runs would still complete, just without answering. The 2525 was surprising at first, but the explanation is the unmatched skip itself: it hands the round to the next list, and 237 lists answer anything. 

U6Engine.Tests   391 / 391   without Unity
U6Formats.Tests  266 / 266
U6Export.Tests    38 / 38

I measured the numbers by running first and pinned them afterwards. A loosened bound, bent until the test passes, is worse than no test.

One contradiction in my own papers

While updating the documents I noticed that the interpreter document claimed as measured something the bug report explicitly declines to claim: whether any of those eight script addresses sits in a region that really does get skipped. The bug report is right, I have not checked. The claim is gone.
