The slot that never asks the type

A spellbook can now be picked up and taken off. Readying it was the missing link: seven earlier slices measured the casting rules, and not one of them was reachable with a real book, because nothing put it on the character's hand in the first place. This slice closes the chain: drop, get, ready, cast.

A question open since the first slice

The spellbook has two slots, two book slots, and nobody was certain why until now. The answer turned out to be simple once it was finally read out of the decompilation: a spellbook readies into a hand, exactly like a sword or a spear. Its tile sits as the eleventh entry of a thirty three entry one handed table. Two hands, two books, one table that knows nothing about spells.

The tile decides, not the type

Which slot an object goes to is settled by eight tests that all ask about the object's own tile, never its type: the feet, a finger, the neck, the head, the chest, two handed, the left hand, or last the one handed table's own thirty three entries. This project already learned a version of this lesson once for weapons, and learned it again here: the type says nothing about which hand, the tile does.

Order is part of the rule, and not a cosmetic detail. A gargoyle belt matches two tests, the neck and the chest, and the neck test runs first. A port that ran the tests in a different order would quietly move the belt from the neck to the chest, and nothing would say so.

A tile nobody explains

One of the neck test's own tiles carries the decompiler's own question mark: /*?? (ground tile)*/. Its number sits in the general animation tile range, far from every other neck tile. There were two honest choices: drop it as quiet tidying, or keep it and say out loud that its presence has no known reason. The second is the more honest answer, and it is the one that reached the code.

Ten and twenty, not one number shared

Worn weight may be at most ten times strength; carried weight, twenty. A character carries twice what they can wear. Both limits were already built ahead of some earlier measurement, and this slice was only their first real caller, but checking that each number actually uses its own constant still belongs here: sharing one number between the two would have been the obvious simplification, and exactly the kind that looks right until something gets worn right at the edge.

A one that is not an object

A two handed weapon takes the right hand and marks the left "taken" with the value one, a sentinel and not the object's own id. A port that put the weapon's own id in both hands would look right in every test where nobody asks what is actually in the left hand, and wrong the first time somebody does. Nothing here stores a slot anywhere in the first place: occupancy is folded over the tiles of whatever is already worn, on demand, so the question "what object is in the left hand during a two handed weapon" never has to be answered wrong, because it is never asked at all.

A table that was found, not borrowed

The one handed table, thirty three tiles, is this slice's only real data table; everything else is a scalar boundary with no byte shape a program file search could ever look for. The table was located in the owner's own GAME.EXE rather than trusted from the decompilation's own comment: the right reading hits exactly one place, and four deliberately wrong readings (the wrong byte order, reverse order, two entries swapped, every value one lower) all hit zero.

Two gaps left named

Returning an unlit torch to its own stack when it comes off, and the world clock's own write to the storm cloak's magic effect, are both left unbuilt: each needs a system that is not here yet, and the brief scoped this slice to two unready rules, not three.
