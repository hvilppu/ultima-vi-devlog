The answer that was always no

The Attack command asks, in three places, whether a target is undead, and all three answered no, every time, even though only two of them were labelled as a stand-in. Nothing cared about the answer for a long time, until a measured undead halving rule and two party-ring spells started needing it, and neither had ever once fired. This slice gave it a real answer, from a class table that already existed for two other purposes, and proved the effect end to end rather than only as an isolated rule.

Three places, not two

Two call sites were a stand-in written plainly on the line: isUndead: _ => false, commented "named simplification". A third was not labelled at all, because it never supplied a stand-in value in the first place: it left the whole parameter out of the call and relied on the method's own default, which happens to be the same false. The method's own remarks had already named the gap, but never counted it as a third, separate call site. A stand-in whose other half hides behind a default value is exactly the shape in which a later reader finds two of three and calls the new ones from the wrong places, the same mistake this session has already recorded once elsewhere.

One reader, not a fourth way to ask

The undead flag is one of the fifteen class trait bits, exported several slices ago, and the view already loads the whole class table for two other purposes: applying a hit and generating a creature. The answer was therefore a lookup it could already make, not a new measurement. The new reader reads the same exported string one earlier reader already reads for three other traits, the same way, rather than repeating that scan down a new code path.

Two different bits, not one with two names

Repel undead reads the undead bit. Fear reads the immune-to-death-spells bit, not undeath: the exact distinction an earlier slice measured months ago as fear's own gate. These are two different bits in the same table, and one class in this game carries death immunity without undeath: a reader that confused the two bits, or treated one as standing in for the other, would score exactly this one class wrong while every other class would still come out right. The test uses this one class precisely because it is the only one where the confusion would show.

The halving fires end to end, not just in isolation

The undead halving rule already had its own test, with synthetic always-yes and always-no stand-ins, and that test had been passing the whole time. It never proved what it looked like it proved: in the running game the stand-in always answered no, so the rule had never actually fired. The new test builds the question exactly the way the view now builds it, from the real class table, and shows the difference between a skeleton and a giant rat: same weapon, same seed, the skeleton's damage always lands on one while the giant rat's does not.

A finding, not a fix

The original's own fear spell also excludes a target whose alignment is exactly good, in the decompilation's own code. This exclusion has never been modelled in this project, and no remark names it as deliberate: it is an existing gap in an earlier slice, not this one's. This slice's own scope was wiring the classification, not changing a rule that was already built and tested, so the gap is recorded rather than fixed.
