Ten pointers out of a table of five

You can make a wish at a fountain. The routine reads the typed line and compares it, in a loop, against ten pointers from an array that holds five. The decompilation's own comment marks that as a bug and leaves it there. What those five extra pointers are is a question only the owner's own GAME.EXE can answer, and it was worth reading, because it decides whether this port is narrower than the original.

First: five words that do not enter this repository

The wishes are the original's own text, so they travel the road the eight mantras already travel: this tree holds only offsets and lengths, the words are read from the owner's file at export time, and the export writes a 40 byte file into a gitignored directory. The leaked-text check finds nothing, which is the measurement that says the words did not get in here.

The discriminator is double. Four of the four gaps between offsets are the earlier word's length plus its terminator, and at the measured base all five land as letters followed by a zero byte, while a base moved one byte either way lands none of the five. And on top of that: the array's own pointers are exactly the five offsets the decompilation tags beside the literals. So the table is not merely consistent with the tags; it contains them.

The five extras, read

pointers 0-4   0x2587 0x258C 0x2593 0x2598 0x259E   the five words
pointers 5-6   0x100  0x101                         the tail of another literal
pointers 7-9   0xFF00 0xFFFF 0xFFFF                 past the module's own data

Pointers 5 and 6 point at four and three byte runs that end in a newline. A player cannot type a newline at a keyboard prompt, so those two can never match: the harmless half.

Pointers 7 to 9 point past the module's own initialised data, into the segment's zeroed area. What is there at the moment of the comparison is not in the file. If that byte is zero the pointer reads as an empty string, and then pressing Enter alone would match and earn the one-in-five chance of food. That is not claimed either way here, because the file does not say; entry 3.41 records it exactly that way.

And this is where the port is deliberately narrower than the original: there is no data segment here to read past. A wish this refuses is one the original might still have matched. It is named in a test rather than buried in a comment.

The rule itself, and two numbers that happen to be the same

The question, one key, and anything but yes is a refusal: the original tests one letter rather than looping over two the way the save confirmation does. Yes opens a nine character line. The match is case insensitive, the first match wins, and one roll in five grants food.

The roll happens before the weight test, so a wisher who cannot lift the meat has still spent that one-in-five. And the weight test is the original's own literal: it adds 2 to the load. The portion of meat's own weight byte is also 2. Two different facts that happen to be the same number, so the rule follows the literal and a test asserts the coincidence separately. If they ever differ, the test says which one this port keeps.

A wish the table does not know costs no draw at all. That is the measurable side of one shared random stream, the same kind of thing the hail storm turned up.

For the third time: an expectation is a claim

The plan's table said the fountain waited on text entry. Text entry was built with the rune's mantra prompt long ago. This is the third time in this batch that the same column sent me the wrong way: the silver horn and the cannon both said "combat" and were waiting on something that already existed. An expectation goes stale exactly the way an absence claim does, at the moment the thing it waits for is built, and nobody returns to the row that recorded it.
