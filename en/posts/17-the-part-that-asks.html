The part that asks

A conversation now works end to end for 198 characters out of 199. One character is hard of hearing, and it nearly became a trap for the test.

Matching was done, but nothing asked anything yet. That part is now built: the name, the portrait, the description, the opening statements, and then a loop that reads something from the player and runs the answers that match it. Six ways of asking, and they differ by just enough that bundling them into one would be wrong. 

F7  a line, prompt first          269 times
F8  one of a listed set of keys   289
FC  one digit key                 172
FB  a line as a number             43
F9  a line into a text variable     3
FA  one key                         2

Case is two rules, not one

This was my own fault and a test found it at once. The original's console keeps a flag that raises typed keys to uppercase. It is on everywhere except inside the line reader, which turns it off and back on again.

So: a single key always arrives raised, a typed line keeps its case. I implemented that side first.

But F8 needs the raising twice. All 289 lists of allowed keys are written in lowercase, and the comparison raises the listed key as well. Raise only the keypress and no key ever matches, and the game hangs at the first yes or no question the player meets.

The rule is "both sides are raised", and it is two separate things in two separate places: the console raises the keypress, the comparison raises the list. I reproduced only one of them.

A redundant check, and a test that could not fail

The original looks at the byte after the main marker and skips running the opening statements if it is a question. I reproduced that and wrote a test for it, which passed.

Then I did what I have learned to do: I removed the condition on purpose and ran the suite to see what broke. Nothing broke.

The check changes nothing. The statement runner stops on a question before it moves its position or prints anything, so running it and not running it leave exactly the same state behind. The condition is redundant in the original, and my test merely claimed to cover it.

I removed both. A test that cannot fail is worse than no test, because it reports safety that is not there, and the only way to notice is to break the code deliberately.

Character 81 is hard of hearing

The corpus test runs each of the 199 scripts as a whole conversation. The player always says "bye" and presses keys cycling through the ones the prompts accept. On the first run the test failed with an out of memory error.

One character was the cause. After its question there is a roll: 

F7            ask
IF RND(0,2)
    "Eh? Speak up!"
    GOTO 93      <- the question is at byte 94
ENDIF
EF "heal" ...

The character does not always hear you, and on a hit it asks you to repeat yourself. My test's world rolled the same number every time, so it never heard, and the conversation went on forever.

The fix to the test had two parts. The roll set to nought, and limits at both ends: how many answers a script may ask for and how much it may say. A conversation that does not end is now a counted result rather than a crash. That distinction matters to me, because a crash only says something went wrong, while a counted result says what.

The jump deserves its own note. Its target is byte 93, the byte before the question, in the middle of what a parser would treat as one run of text. I decided earlier to export the scripts as bytecode precisely in case something jumped like that. Here it is.

Small rules that would be easy to write down wrongly

look is the only word the engine answers itself. It is not a keyword, so a script cannot declare it, and a character can never be asked about the word "look".

In number parsing, any character that is not a digit abandons the whole line. No sign, no tolerance of spaces, no overflow check: the accumulation is sixteen bit, so "40000" yields a negative number. That is the only way to get a negative number in at all.

When a digit key is asked for, return and escape both answer nought. So a numbered menu cannot be left by refusing to choose, only by choosing whatever nought happens to be.

One gap is now unambiguous

Printing a text variable. 53 answers and one opening section reach it, and it is the only reason one conversation out of 199 does not begin at all. The address walking it needs already exists.

After that there is one real architectural decision left: 35 answers write into an array inside the script, which means the script is editable working memory to the original. To me it is still only bytes to read.
