All 196 conversations

The conversation corpus has measured one thing for a long time: how many characters can be talked to from the first word to the last. It was 172, then 190, 191 and 192. It was 192 because one opcode refused, the script's own way of setting a character's AI mode. That is built now, and the count is 196 of 196.

The refusal was a sentence that had once been true

The conversation adapter threw for that opcode with the reason "nothing acts on a behaviour yet". Nobody had looked at it since it was written, and in the meantime 73 places in this project read a character's behaviour: the combat AI, the alarm, camping and the idle animation all drive on it. The same adapter reads it itself, one method up.

The opcode does three things

It would have been tempting to write one line: set the mode. Read, the handler does three things:

  • writes the mode, validating nothing, so a value no named mode covers is stored anyway
  • if the mode is sleep, also sets the asleep bit and takes the character's unconscious shape
  • if the mode is anything but play, turns a short caped musician into a long caped one

And the order of the last two is load bearing

The sleep branch changes the character's type, and the musician test reads the type afterwards. So: a short caped musician put to sleep takes the dead body shape and stops being a short caped musician, and the cape swap never fires. That is not a rule anybody wrote down; it falls out of the line order alone.

A test drives exactly that, and names why the frame cannot tell the orders apart: both capes share a corpse frame, so only the type separates them. If the cape swap ran first, the result would be a corpse with the same frame by a different route, and a frame comparison would accept both.

One condition left unmodelled, and why that is a measurement

The unconscious shape swap is conditional in the original: it does not happen if the type's creature class is a vanishing one. I left the condition out, and that took two measurements from the owner's own program: 

vanishing classes of the owner's 64                          8
their types in the corpse shape table                        0

types in the corpse shape table                             23
of those with no creature class                              2

So for a classed type the condition cannot fire, because no vanishing one is in the table. And the two without a class? For those the original asks for class -1 and reads in front of the flag table. Measured in the owner's GAME.EXE, that word is 0x6000, which lacks the vanishing bit, so they take their shape too.

Applying the swap unconditionally is therefore exactly right on this copy, and the reason is written down rather than assumed. The read outside the array is a finding of its own and goes into originalBugs.md.

The measurement is split across two assemblies rather than copied: the engine cannot see the monster table, so the word and those eight types are pinned by the formats library's test, and the 23 types the measurement was scored against are pinned by the engine's. Keeping two halves apart is cheaper here than copying a table across the boundary.

What 196 does not mean

A conversation counts as finished when it ran from start to end with a player who only ever says "bye". It does not mean every branch is right. Eleven members are still unbuilt, and none of them stops any conversation: one of them is MoveObject, which stands as proof that an unbuilt member can sit behind a branch nobody walks.
