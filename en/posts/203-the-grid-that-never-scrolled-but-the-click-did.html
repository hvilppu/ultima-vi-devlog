The grid that never scrolled, but the click did

The document debt list's next sweep found three stale comments and one real bug. The bug is the interesting one: the equipment view's own pack grid always drew the same twelve items, but a mouse click landed on whichever square would have shown if it had actually scrolled.

Two readers, one scroll value, different sources

_invenScroll is the real, moving scroll value U6InventoryScroll's own arrows write, and ComputePanelEquipContext feeds it into the pointer's own hit test. But DrawEquipViewFromPanel, the pack grid's own draw, still read U6StatusPanel.InitialScroll, the constant nought. Both readers were supposed to read the same value and did not.

Why this looked like it worked

The scroll looked fine because nothing ever drew anything but the first twelve items. A click, though, landed on the pointer's own real scroll value, so a scrolled click would have picked the wrong item: a silent mismatch between the draw and the hit test, not a visible crash.

What the fix does not cover

The original resets InvenScroll to nought every time the panel is shown, STAT_ShowInventory (status.c:454-457), from five separate call sites. This project has no matching reset anywhere. That is not a new gap: the hit test already read the same unreset field before this fix, so a wrong pick across a character switch was already possible. Drawing from the same field just makes the mismatch visible instead of masking it. Finding this project's own equivalent of each of the five call sites is its own slice.

Three stale comments, found by the same sweep

Two copies of the same claim (in the cast wiring's own remarks and the test creature spawner's own remarks, both in U6View.cs) said summon and conjure were not connected to the creature generator. They have been for months. And _defaultCommand's own field comment said ClearForLoad had no caller, when the line right beside the real call (U6View.cs:1797-1798) already says in as many words that it does.
