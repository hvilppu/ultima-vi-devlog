The star that wraps to a high byte

M20's second piece: the ending's own starfield, 64 stars flying out from the Codex's own centre. Building it also turned up a claim of my own that failed its own test before it ever reached a commit.

One step per star, every tick

Each star moves away from the centre (56, 47) on each axis independently, at a speed that rises with distance. A star that leaves the field is reborn at a random place, its colour unchanged.

A claim that did not hold up

The original's own starX/starY are bytes, so a star overshooting past zero toward the centre wraps to a high byte (minus three wraps to 253, for instance). I first wrote this up as a discriminator: that an ordinary signed zero check would answer differently from the byte wrap in exactly this edge case.

That was wrong, and my own arithmetic caught it before it shipped. The field's own largest single-tick step is four on the X axis and three on the Y, since the greatest distance to the centre is 56 and 47. The smallest possible undershoot always wraps to at least 252, which is past the field's own bound either way, wrap or no wrap. The wrap is kept because it matches what the original actually does, not because it changes the answer.

Two things left to the view

There is nothing to erase in this project: the original keeps one persistent screen buffer, this project recomposes every frame from scratch. "Draw only on black" is the view's own question too, since it needs the composed background, the same split the hail storm's own stones already use.

The colour cycle waits on one question

EndTick's own rotation of palette slots 16 to 31 is small but it waits: which runtime representation the Unity side actually holds a loaded palette in. The export-time U6Palette is not it, and nothing on the Unity side references it except through the shared file list. That is its own measurement, not something to guess at along the way.
