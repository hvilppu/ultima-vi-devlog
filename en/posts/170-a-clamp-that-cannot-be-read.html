A clamp that cannot be read

The drop was a quarter of the original's command. Now a thing flies eight tiles, shatters if it was breakable, and goes into a container if one is standing there. And the brief's proudest measurement was wrong, in a way that needed another routine opened to see.

Four of the five absences existed

The drop command's own remarks named five of the original's rules and said they needed "systems that do not exist": the longer throw, the breakables, the line of throw, the movement points, and asking how many. Four of the five were already built. The missile trace already had a range parameter, the movement cost was a named constant, and the breakables had a class. Only asking how many was genuinely missing.

This is the same pattern as the previous post: a sentence claiming an absence that nobody went back to check. This time there were five in one paragraph, and the same paragraph was repeated one file over in the view.

A clamp that exists and cannot be seen

The brief described the line-of-throw check like this: the missile call takes its destination by pointer and writes back the square where the throw stopped, so the call both tests the line and clamps the aim, and everything after it reads the clamped square. That was an exact observation and it led to a wrong conclusion.

The build run opened the routine's body. The write-back happens only in the branch where the shot did not reach, and the same branch zeroes the return value. The command, in turn, refuses and returns on exactly that return value. So the clamp is written only once the command is already over, and it can never be read. A blocked line is a full refusal: nothing moves, nothing is spent, and nothing lands nearer.

The brief's first discriminator was therefore describing behaviour that cannot happen. The run replaced it with the refusal and proved the refusal by breaking it: it put the old reading back and watched two tests fail as predicted. This was the sixth time in one night that I cited one property of a routine whose body I had not opened, and the second time for this very routine.

An object number, not a type

The container test is a nineteen-line routine in which one variable name carries the container's type for four tests and then the item's type for the last one. But the more dangerous part comes before that: the test requires the item's object number to be at least 0x100, not its type. Numbers below that are actor slots, so the real rule is that a creature cannot go into a container.

Read as a type test it would refuse almost all of the game's furniture and all of its food. The run proved that by making exactly that mistake on purpose and watching a sword refuse to go into a barrel.

A range that only binds diagonally

The throw's range is eight, and it was used in the code without any test asserting it. Measuring showed why it is awkward to pin: the original gates on three things in the same line, each axis delta being at most seven and the range table's own value being at most the range.

So the seven binds every straight line, and the eight can only bind diagonally, where both deltas are inside seven but the distance between them exceeds eight. That is the only place a test can see the eight at all. Three tests pin it there from both sides, and the boundary one fails with the range at seven and passes at eight.

Three side findings reported rather than hidden

The push path's support question was hardcoded to false for want of the predicate, and now calls the real one. Three more stale "these do not exist" comments are gone, because this slice's own predicates falsified them. And the movement cost constant now names both of its callers, getting and dropping, instead of one.

One real divergence went to the debt list rather than being fixed here: ground placement splits a dropped pile at 144, which is the original's rule for adding to a stack rather than for dropping, whose own placement is a single call with the whole count. It is reachable, because the starting world holds stackable piles up to 240.
