A plausible no

I promised a number and here it is: 172 conversations out of 196 get through against the real world. The more interesting part is why the number is measurable at all. It is measurable because the unbuilt world refuses to answer.

The conversation engine has been finished for a while, and the corpus test has run all 199 scripts from start to finish, 199 times out of 199. But that number is measured against a world double: a class that answers every question with something. It says whether the interpreter works. It says nothing at all about whether the game works.

This week I built the world that actually exists. The interface has 32 methods, seven of them answer, and the other 25 do not, because there is nothing underneath them.

What an unbuilt member returns

There was one real decision here, and the whole measurement rests on it.

The tempting option is to return nothing: carries none of those, not wounded, not in the party. The code compiles, nothing crashes, and all 196 conversations get through.

Which is exactly why it is worse than a crash. A script that asks "do you carry a key" and is told "no" does not fail. It takes the other branch, says something else, and looks precisely as working as a conversation that was answered correctly. The number of conversations that get through would be 196, and it would measure nothing whatsoever.

So every unbuilt member throws, and the exception names itself: 

The world cannot answer WhoCarries yet: inventories are not built.

The test catches the name and counts. One test run now reports not only how many conversations get through, but which missing structure stops how many, which is the order to build the rest in.

Inventories are 21 of those 24, and a single member is 15 of them. The other twenty unbuilt members stop no conversation at all.

Last post I guessed the number would not be complete, because object calls are 28 per cent of all world calls. The guess was right, but a great deal sharper than I could have guessed: it is not 28 per cent, it is one question.

You cannot ask the pixels about visibility

Before the adapter came the half that was left over last time: the other half of being on screen. The geometry was done, but the rule also requires that the square actually be showing something.

The composer already worked that out, but it produced nothing but pixels, and a finished image cannot give it back. A dark pixel might be darkness or a dark wall. So visibility has to be recorded while drawing rather than inferred afterwards, and the composer now remembers two things per square: which tile ended up there after lighting, and whether an object's pixels landed on it.

The second one is marked in the one place where an object's tile actually reaches a square. That is not a matter of taste: a wide or tall object passes through that point four times, and marking it where objects are picked instead would make a wide object cover one square.

Correction. This originally said a wide object marks all four of its squares, as the original does. That was wrong, and the refuter round in post 24 found it: the original asks, for each tile, about the target square's own tile, and records nothing when that square is dark or hidden. Measured, 897 dark squares carried an object and should not have.

A character standing in an unlit room is now not on screen, even from three squares away.

What 172 is not

It is not a grade for how finished the game is, and that is worth saying out loud before I forget it myself.

A conversation counts as getting through when it ran from the first word to the last with a player who only ever says bye. A branch that was never asked for cannot stop. So 172 is a floor on what is broken, not a ceiling on what works, and the real number is somewhere below it. The test asserts this as a condition of its own, so that nobody reads the number wrong later.

The remaining three of the 199 are scripts with no character of their own. They are reached through a world object, and there is nobody to stand in front of, so they are not in this run.

One rule left unbuilt on purpose

While the party is aboard a vehicle, every player-controlled character counts as being on screen. The rule is read and written down, but there are no vehicles, and a condition nothing asks about is not worth guessing into place. It sits in the document under what is still unimplemented, which is where it belongs.

Correction. I first wrote this as "a player-controlled character sitting in a vehicle", which reads as per-character occupancy. The condition has two halves and the second is global: it is the party's control state, not who is sitting where. One flag turns the answer to yes for all of them at once, wherever they stand.

A mistake of mine that only the tests found

One of those seven answering members is a character's name, and I wrote it wrong in two ways. I gated the name on party membership, and I walked sixteen places.

The original does both differently. The gate is the top bit of the character status byte, "the player commands this one", which is a different question from being in the party. And the loop walks eight places, because the party cannot grow past eight.

Neither mistake broke anything. In the corpus run a name is only ever asked about party members, so both readings answer the same for everything the data asks. The mistake surfaced only because I started writing the class its own tests and read the passage in the decompilation to do it.

That turned up a quirk of the original's own: the loop breaks on a match and the name is read at wherever the counter stopped, so failing to find anyone reads the ninth name, which belongs to nobody. A consistent game state cannot reach it, because the bit and the places are kept in step. Reproduced anyway, in one line.
