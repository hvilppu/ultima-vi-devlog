The wrong byte and eight colours

A potion is one object type whose frame is its colour, and eight arms. Every effect was already built. One accessor pair was not, and looking for where it belonged turned up a defect of ours: poison was written to the wrong byte, so a poisoned character in the owner's real save read as unpoisoned.

Two objects inside four lines

The routine takes the potion, asks for a target, and then prints the target's name and reads the potion's frame within four consecutive lines. An implementation that read one object for both would compile and look right: it would simply print the wrong name or pick the wrong colour. That is its own discriminator, and it is the only test that catches it.

The bottle is destroyed even when nothing happens

The deletion is after the switch and unconditional. Every arm that refuses still falls through to it, so a red potion given to an unpoisoned target destroys the bottle and does nothing else. Only the two refusals that come before the switch spare it.

The run proved this by breaking it: it made consumption conditional on the arm not refusing, and three tests failed at once. This is the place a sensible implementation would diverge on its own, because "it refused, so nothing was spent" is what anybody would assume.

A bug with only one testable direction

The blue potion tests whether the target is undead, where every other sleep in the whole program tests sleep immunity. The right macro sat fourteen lines from the wrong one in the same header and in two correct uses.

The consequence was measured out of the owner's own exported monster table and it is one-directional: sixteen of the sixty-four classes are sleep-immune and not undead, so they resist the sleep spell and the sleep field and fall asleep from the potion. And no undead class lacks sleep immunity. So an undead target resisting proves nothing, because both readings agree there; only a sleep-immune non-undead class falling asleep separates the bug from a correct implementation. The test is written in that direction and proved by breaking.

And a defect of ours, found from a third direction

The potion's sleep arm needed an accessor pair for being asleep, which did not exist. The build run looked for which byte it belongs on, and found on the way that the poison accessors used the object status byte, where the original keeps poison on the character status byte together with protection, paralysis, sleep, death and player control. All five of those were already wired there correctly. Only poison was not.

The plainest evidence that they share the byte is the original's own resurrection macro, which clears death, poison, sleep and paralysis out of that one byte in a single write.

The run reported it rather than quietly working around it, which is the behaviour worth keeping. It then judged the fix out of scope at seventeen files and left it. Measured, it is three references in one file: the seventeen are callers that go through the accessors and do not change. Fixed in review.

Why nothing noticed

The whole suite passed with the wrong byte, all five thousand tests. The defect was consistent with itself: poison was written to and read from the same wrong place, so nothing running purely inside this project could see it.

It breaks only at the boundary with the original's own data. The bit arrives on the character status byte from the owner's own save record, so a poisoned character in a real save read as unpoisoned, and anyone poisoned on this side would have saved with the bit in the wrong byte.

So the fix came with a test that would have failed before it: poisoning must be visible in the character byte and must leave the object byte untouched, in both directions. Proved by putting the defect back and watching exactly that one test fail.
