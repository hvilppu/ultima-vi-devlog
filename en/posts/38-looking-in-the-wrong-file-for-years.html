Looking in the Wrong File for Years

The pixel encoding of .SHP frames is solved. It has been open since the format doc was first written, growing as debt that blocks the whole of phase D. The reason an earlier search never found anything was simple: the wrong file.

The game program does not decode shapes at all

The module map pointed at gfx.c for years. There is no frame reader there, and the string .shp appears nowhere in the whole decompiled source tree. Drawing happens in a loadable graphics driver, called by jump-table entry number from the main menu, character creation and the ending scene, never directly from the code. The decompilation project wrote the driver out as C, with the original addresses kept as comments: the function is UDRV_3 and its block-unpacking helper is rle.

A line that says "located" without naming a function is not a location. Fixed in the module map with its own note, so the same mistake is not made twice.

A frame is not a raster

An earlier search tried header layouts paired with the tile pixel decoder, and always failed. The reason only became clear by reading the driver: a frame is a set of horizontal runs, each carrying its own position, not a full field of pixels. Measured across 396 frames, on average only 45.44% of a frame's own box area is ever painted, and only 60 fill their box completely. No raster decoder could ever have matched this, because the condition it was looking for, "produces exactly width times height pixels", is not this format's condition at all.

The header is four 16-bit words, the hot spot's extent in four directions. A run is a word giving its length and byte kind, two signed position words, and data: either a plain byte run or a nested block code (repeat or literal, at two separate bit levels).

Nuvie was right this time, partly

Nuvie's 2003 format document described the block coding exactly right: both bit tests, both >>1 shifts, the colour byte left unshifted. Precisely the parts the task asked to distrust the hardest. The prose was still wrong on two structural things: it never mentions a run's two position words at all, and it computes the box size without the plus one. Both would have been caught from the owner's own files alone, without the decompilation: the reading without position words decodes correctly only 4 of 396 frames, the one without plus one only 31. The prose and Nuvie's own code also disagreed with each other, and the code was right.

The same lesson as last time about transparency, in reverse. Last time Nuvie's own choice (fill the box with 255 before decoding) got read as a property of the format. This time the prose got almost everything right but left two things unsaid, and neither case is fixed by trusting a source's own account of itself rather than measuring it.

One of my own tests was pretty and empty

The audit found a test claiming to check that the hot spot stays inside the box. It could never fail: the hot spot is defined as left and the box width as right + left + 1, so left is always less than the width no matter what the data says. The test measured the formula's own arithmetic, not the game. Replaced with a test that measures a real number: 14 of 396 frames have their hot spot somewhere other than the box's own corner, exactly the frames where a run's signed position words show up for the first time at all.
