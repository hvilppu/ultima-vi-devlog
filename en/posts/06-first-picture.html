Rebuilding Ultima VI

Notes from a 1:1 reimplementation in C# and Unity.

← all posts · 06

The first picture

Five milestones of invisible work finally show up on screen, by not using the game engine's tilemap at all.

Up to this point the project had produced a lot of verified data and nothing you could look at. Tiles, a world, sixteen thousand objects, portraits, a font, and 85 passing tests, none of which had ever been near the engine that is supposed to run the game. That is a comfortable place to stay and a bad place to stay: every assumption about how this would work inside Unity was still untested.

Not using the tilemap

The obvious approach is the engine's built-in tilemap: slice the artwork into 2048 sprites, build tile assets, fill a grid. The plan said to do exactly that. I did something else, and the reason is the project's goal rather than performance.

The original drew the world into a window of 176×176 pixels, eleven tiles square, by writing palette indices into a buffer. So that is what the remake does. A renderer composes the window as indices, and colour is resolved only at the final step.

Three things fall out of that choice:

  • It is closer to 1:1. A tilemap inserts its own sprite slicing and pixel alignment between the data and the screen, a whole category of problems that buys nothing here.
  • The day and night palettes keep working. The game ships six lighting palettes. Holding indices until the last moment is precisely what makes them usable; baking colours in would throw them away.
  • It is testable. The composer touches no engine types at all, so it can be driven directly from tests.

Performance was never the argument. The window is under 31,000 pixels.

Testing a renderer properly

"It draws something" is not a test. The strongest check walks every square of the composed window and compares every pixel against the tile the map says belongs at that position, skipping squares that have an object standing on them.

Two more earn their place. One finds a square holding an object and asserts the terrain underneath it actually changed, because otherwise objects could silently fail to draw and the first test would still pass. The other composes a view, composes somewhere else, then composes the first view again and requires an identical result, because the renderer reuses one buffer and a stale pixel is exactly the kind of bug that survives a casual look.

Those run headless from the command line, as does the scene creation, so none of it depends on anyone clicking through the editor.

Where the test count went

SuiteTestsCovers
Format library64decompression, palettes, tiles, map, objects, names, portraits, font
Exporter21image writing, world round-trip, runtime binaries, the command line itself
Engine (in Unity)32data loading and the renderer

That second row only exists because of an uncomfortable question partway through the project: was everything actually tested? It was not. The format library had 47 tests and the exporter had none: the image writer, the world writer and the preview renderer had all shipped unverified. Finding that out led to a rule now written into the project's own plan: tests are written in the same step as the code, they run against the real game data wherever possible, and an expected number is measured before it is asserted rather than guessed and then loosened until it passes.

That last clause is not hypothetical. Guessing bounds had already produced three failing tests that I was tempted to simply relax.

What runs now

Open the scene, press play, and the view moves across Britannia with the arrow keys: terrain and objects in their correct places, at the original's native resolution, scaled by whole pixels so nothing is ever resampled.

It is not a game. There is no player, no collision, no time passing. But the entire export pipeline is now proven end to end in the engine that will ship it, which was the point.
