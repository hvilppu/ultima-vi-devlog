The font that was not there

The font, the text layer and the flags. On the way an open question closed, an original fault turned up, and I had to move a class of my own out of the wrong assembly.

There is no runic font

The text has two escapes that switch a runic font on and off. The font itself was an open question in my own document: I knew the high bit gets set on the character, but not where the runic glyphs came from.

The answer is that they come from nowhere in particular. The runic font is the upper half of the same font. The high bit moves a character into slots 128 to 255, and that is where those glyphs live. One file, two alphabets.

It also explains a number that had been nagging. The font has 256 slots and 245 of them carry a glyph, which is far more than one alphabet needs.

The eleven empty slots are these: 

0  2  9  10  13  32  128  137  138  141  160

Six from the lower half and five from the upper. Note that slot 2 is empty while slot 130 is not: the upper half is not a copy of the lower, and an implementation assuming it was would be wrong about exactly one slot. That is why the test pins the list rather than the count.

The escapes, and two numbers that say something

I measured how often each is used before implementing anything, so that I knew what I was building. 

@  1681 / 192 scripts    keyword highlight
$  1170 / 160            text variable
*   748 / 199            wait for a key
#   326 /  91            number variable
\   25 /  21            plural form
`     7 /   6            capitalise next
&     6 /   6            gargish section
%     4 /   4            cancel
^     3 /   2            special glyph
/     2 /   2            singular form
<     1 /   1            runic font on
>     0                  runic font off

Two rows stand out. The * escape is the only one every one of the 199 scripts uses. And the runic font is switched on once in the whole game and never off.

The numbers were measured twice. The first measurement showed one too many of each, because it read a script's header as code and a character number can happen to be an escape: character 60 is < and character 62 is >. The same trap caught me earlier with character 181. The second time is easier to spot than the first, though evidently not easy enough.

A class of mine was in the wrong assembly

I wrote the conversation panel on the Unity side, because a window sounds like a Unity thing. The pre-commit check pointed out that it had no tests, and when I went to look at why, the reason was that it could not be tested without Unity.

Except that it could. The class used nothing from Unity: the whole panel is index arithmetic. The only Unity reference was a needless using line I had written out of habit.

I moved it into the engine and wrote tests for it. The project's rule says anything that cannot be tested without Unity is in the wrong assembly, and this was a reminder that the same holds in the other direction.

The session is a state machine now

In the last post I ran into the fact that a frame loop cannot block, and my input interface blocked. There were two options: the session on its own thread, or the session as a state machine that returns to the caller to wait.

The state machine won. Begin runs to the first question and says what it wants, Answer takes it to the next. The whole input interface disappeared along the way: when the caller supplies the answers, the session has nothing to ask for.

Two things improved as a side effect. A rejected key is no longer an error but the same need again, which is exactly what the original does. And the allowed keys are public now, so whatever draws the text can say which keys will do.

The best evidence that the conversion preserved behaviour: the corpus test's pinned numbers did not move. 199 out of 199 conversations begin and end, and they take exactly 212 answers, the same as the blocking version.

One thing I did not quietly paper over. The original's wait instruction stops the statement runner mid run, and here it is a signal to the text layer. Where the wait only paces text the difference cannot be seen; where a script changes the world just after one, the change now happens before the key. Being exact would mean carrying a resumption point through the whole interpreter, and nothing measured pays for that yet.

Flags, and measuring before building

The world interface has 32 members. Rather than guess where to start, I counted how often each is called: 2563 calls across the whole data, and three structures cover 85 %. 

flags    788  (31 %)   TestFlag, SetFlag, ClearFlag
objects  722  (28 %)   HasObject, TakeObject, GiveObject, ...
party    667  (26 %)   PartyMember, IsInParty, ...

Three members are never called at all. They get a clear refusal rather than a guess.

Flags first, because they are the largest group and have no dependencies. The original keeps eight flags per character, one byte, a 256 byte block saved as it stands. Bit nought means the player has met them, and the scripts set it 274 times out of 422.

And an original fault alongside

When the player looks at a character, the game chooses between a generic description and the real name using the met flag. The condition is written like this: 

!TalkFlags[objNum] & 1

C binds the exclamation mark tighter than the ampersand, so this asks whether the whole flag byte is zero, not whether the met flag is clear. As soon as any flag is set on a character, the game treats them as met.

I did not leave that as theory but measured who flags are set on. 321 writes target the character being spoken to, the rest a literal number, and among those character 178's script sets five flags on character 146. Talk to 178 before meeting 146 and 146's real name shows at first sight.

What I did not check: I have not run the original to see it. Reproducing it waits for the code that chooses a name, so the fault can be neither imitated nor skipped right now. Recorded so that it gets built wrong deliberately rather than right by accident.
