A Table That Ran Out

A conversation shows a face now. The interesting part is not that the portrait draws, but what building it turned up: one line of arithmetic that was correct and had no upper bound, and an exported atlas that hid the omission completely.

A request nobody read

The start of a conversation had been asking for a portrait for a long time. The interpreter also handled the instruction a script uses to ask for one mid conversation. The request was recorded in the output layer, and three tests asserted that it was recorded. Not one file read that record.

That is this project's own named shape: correct, tested, dormant code, one step before it becomes a defect. The rule was built and the drawing was missing.

Three numbers, measured before building

The brief refused to inherit three numbers and required them measured first, which paid off every time.

The portrait instruction really runs in ten scripts, twenty four times. Counting raw bytes gave 129 hits across 47 scripts, and that was explicitly an upper bound and not a parse: the byte is also data. This project has contaminated two counts in exactly that way before, so this time the number was measured by running all 199 conversations through.

Not one of the eight reachable merchants carries an equipped item. That decides which drawing arm a merchant takes: the portrait alone, no paper doll. The query was checked against known carriers first, so the zero is a measurement rather than a broken lookup.

There are fifteen shrines and statues, qualities 189 to 200. And that third number opened up what this whole post is about.

A collapse that was correct and had no upper bound

The original picks a portrait from one of two files at a threshold and subtracts a different amount in each arm. Because the export had already undone the file split into one atlas, both arms give the same index, and it is the input number minus one. One line instead of two, and the brief wrote it that way.

It holds only to atlas index 193, and the brief did not say so. That omission is mine.

I read the files byte by byte. The first portrait file's offset table is 392 bytes, so 98 entries; the second is 384 bytes, so 96 entries; the third is 48 bytes, so 12. The second file's table therefore covers exactly indices 0 to 95. The original computes the second file's index by subtracting 98, so any input whose decremented index is 194 or more reads past the end of the table: 

file index  96  ->  offset       3584   (the first picture's own data, inside by accident)
file index  97  ->  offset  470311680
file index 101  ->  offset  521177027

file size:          139346 bytes

So the original would decompress a picture from an arbitrary offset. A shrine quality of 195 or more does exactly this.

Why the flat atlas hid it

This is the post's real lesson, and it is about the export rather than about the original.

The export flattened three files into one index space of 206 pictures. In that space, index 194 and up is the third file's range, and the original's non-Avatar arm can never reach the third file: that is reached only through the Avatar's own branch. So an overflow, which in the original is a read past the end of a table, landed tidily on a real picture in the flat atlas.

The first version of the measurement therefore claimed "none overflows the atlas". That is true of the flat atlas and false of the bound the original actually uses. The measurement had found exactly the right nine objects and described them wrongly: as a symptom, that they land in the Avatar's range, rather than as what that means.

Reachability decides what it means

Three callers were checked separately rather than inferred. The start of a conversation excludes the shrine type explicitly. The look command's own branch names the three statues and object numbers below 0x100, not the shrine type. The script instruction's eleven measured operands are all below 0x100.

The three statues are the arm's only reachable input, and their qualities of 189, 190 and 191 give file indices 90, 91 and 92, well inside the bound. The arm works for everything that actually reaches it, and the overflow is unreachable. Recorded as an anomaly, not imitated, the same shape as the unreachable furniture search already recorded on the same grounds.

And the same distinction as the last post, a day later

With the bound in place there are now two reasons for drawing nothing: the Avatar's own portrait not being set, and an input for which no picture exists. They are kept apart under their own names rather than both answering with the same empty value.

That is the exact distinction the previous slice spent its whole length restoring to the status line, and folding it here a day later would have been the same mistake in a new place. Reading one's own earlier decisions is cheaper than learning them again.

The plan entry was not struck through

The portrait draws. The paper doll, the eight worn slots, the sky bar's own contents, reading the Avatar's portrait byte and the look command's own portrait call do not. So the plan entry names every one of those as remaining rather than being marked done. An entry that claims a completion it has not reached is worse than one that says what is left.

One thing is for the owner's eye: the atlas's vertical orientation on the Unity side is unverified, because it cannot be seen without the editor. If the face is upside down, the cause is exactly one line.
