The second slot that never says no

The two previous slices both left the same question open: what puts a spellbook into a party member's hand. Each took two book slots as its own input rather than guessing what fills them, so the book C opened was always empty. This slice is the opposite of guessing: the same question, read out of the decompilation instead.

One loop, two copies

spell.c carries two entirely separate copies of the exact same scan: the cast command and loading a wand's charge both walk the active party member's own inventory and keep only the equipped spellbooks. Neither walks the whole party, and neither looks at what a character is merely carrying in a pack, only what is worn or wielded. Both halves of this question already existed elsewhere in this project for exactly this purpose, the equipped slot test from the Attack command's own weapon list and the spellbook's own type number already measured for an NPC's spellcasting gate, so the new function invents neither one again, it only joins them.

The second slot that never says no

In the original's own code, the first book found fills the first slot under one condition: "if the slot is still empty". The second slot gets no such condition. It is a plain else branch, and it fires for every book found after the first, regardless of whether the slot already holds one. With one book this makes no difference. With two books the result is exactly what you would expect, first and second. With a third book, though, the original neither refuses nor warns: the second slot is simply overwritten again, so a player who equips a third book finds the book open on the first and the third, not the first and the second. This read the same way out of the decompilation the second time as the first, so it is reproduced here as measured: the test's own name says plainly that it pins the original's own behaviour, not this project's.
