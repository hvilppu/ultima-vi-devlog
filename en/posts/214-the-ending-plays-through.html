The ending plays through

The last post left M20 with one thing remaining: wiring every measured rule into one scene that actually runs. That wiring is done now, and along the way one thing turned up that had never been measured at all.

One class, not a view

The plan was to write the wiring on the Unity side, as the view's own code, because it is the view's own job: drawing, input, timing. But every class it drives (U6EndingStars, U6EndingLensRise, U6EndingDraxinusomLens, U6EndingCodexTransitions, U6EndingSceneAdvance) lives in the engine assembly, testable without the editor. This project's own standing rule exists for exactly this: the combat and character rules once went into the Unity assembly against the plan, and the price arrived as rules that could not be proven without the editor. So U6EndingSceneController is an engine-assembly class, not Unity code: it owns both lenses, the star field, the Codex's three dissolves and all 16 text pages, drawing straight onto a real U6Screen. Only the colour cycle stayed on the view's own side, since it mutates Unity's own Color32[] directly, exactly as its own measurement advised back when it was written.

What had not been measured

Halfway through, the wiring needed two numbers no earlier measurement carried: where on screen each of the 16 text pages' own backdrop and text land, and which of ShowAround's three strips actually reaches the Codex box. The second one was a small surprise: the box's own rightmost six pixels and bottom thirteen rows do belong to one of the three strips, even though they sit inside the box's own bounds. An ordinary screen repaint therefore reaches a smaller rectangle of the box than the box itself, measured straight off main.c's own numbers rather than inferred. Both are now recorded in docs/u6-lopetuskohtaus.md.

Two new exported files

END.SHP's frames and END.EXE's text pages are read by a library neither the engine assembly nor the Unity assembly references: a real boundary this project enforces by building, not only by naming. The fix is the same one the rest of this project's data already takes: decode it ahead of time in Tools/U6Export, which may reference that library, and read it back with a small engine-side reader that needs no such reference. Two new files, ending_shapes.bin and ending_text.bin, both round-trip tested against the owner's own files.

A development key, because the real trigger is still blocked

Using the vortex cube is what the original would start the ending from, but it is M13's last usable object type and still blocked. F13 starts the scene directly instead, the same shape F9 through F12 already use for other things stuck behind an unfinished milestone.

What was deliberately left out

END.M's own playback: the song changes are queued but nobody plays them yet. The whole-screen FADE_in/FADE_out crossfades: a direct draw instead, since the Codex's own dissolve fits the existing 176 by 176 work buffer and a 320 by 200 whole-screen crossfade does not.
