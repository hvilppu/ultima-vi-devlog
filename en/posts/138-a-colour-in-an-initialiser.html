A Colour That Was in an Initialiser

The panel has a default view now, so that black rectangle is a party list. But the post is about what checking it turned up: every line of text this project has ever drawn was the wrong colour, and the right one had been sitting in a variable initialiser the whole time.

Four briefs said "not measured, do not guess"

The panel's background colour has appeared in this project over and over as "the paper colour is not measured and is not to be guessed at". That sentence is in four briefs, in several code comments and in the layout document. Two of those briefs I wrote myself.

The colour was here all along, in an ordinary variable initialiser, not in prose and not in a comment: 

ColorPaper = 0x31   (49)   =  255, 246, 194   parchment cream
ColorText  = 0x48   (72)   =  129,   0,   0   dark red
ColorGreen = 10, ColorRed = 12, ColorBlue = 9, ColorBlack = 0

The right-hand column is read from the owner's own exported palette, so the measurement has two sources: the original gives the index and our own data says what is at it.

And what that revealed about this project

This project has drawn all of its text at index 15, which is pure white. The original's text colour is 0x48, a dark red. The names in the panel, the lines in the message area, the conversations: all the wrong colour.

And no test saw it, because the existing assertions only checked that the ink was not zero. That is exactly the shape of test this project otherwise hunts for: an assertion that looks like a test and passes with the wrong value in.

How it was found, and this is the post's real point

A build pass had added two colours to the party list for hit points, green when poisoned and red when low. It named them honestly in its report: "this view's own pick, not measured, the same gap NameInk already carries".

The numbers were 10 and 12. They were exactly right. The reasoning was a guess, and the guess landed. That is precisely the failure this project's rules exist for: a plausible number with a plausible-looking justification that nothing knocks over.

Because the report said "not measured", I went to see whether it could be measured. The answer was yes, on one line, and on that same line were two more colours, one of which showed the project had been wrong from the start.

An honest report found a defect the report itself could not see. Had it written "measured" where it wrote "picked", nobody would have gone to look.

The panel has a default view

The original never leaves the panel empty: it keeps a party list there whenever nothing else has asked for the space. Five rows at a time, each with the member's tile, their hit points and their name, and scroll arrows when the list is longer.

Hit points are green when the member is poisoned and red when they are below ten. And the row's tile is the original shape facing south, not the live one, so a disguised character shows their real body here. That is its own discriminator, because the wrong field would otherwise pass unnoticed.

The rule two slices deferred

The original shares one screen region between several routines, and two slices had recorded "we do not reproduce whichever-asked-last-wins" as an open question. It is two sentences and neither is a guess.

The refresh draws exactly one view per pass, chosen by the view state. The conversation's two routines draw straight past it and put back the value they found. So whichever drew last owns the pixels, until the next refresh repaints the view the state names.

The same sentence says why the party list is the fallback: it is the value the state holds when nothing else has set it.

And the arrows live in the gutter

The scroll arrows are drawn in the full-screen clip, at the column that is the eight pixel gutter left of the panel. That answers a question an earlier brief of mine left open: why the panel's fill starts at 168 rather than 176.

One discriminator came out the other way, and is recorded that way

The brief asked for proof that the direction-frame classifier's arm order is load bearing, by finding a type that satisfies both one arm's open-ended range and a later arm.

No such type exists. Every type a later arm names sits below the range, the nearest by two. The order is still built as the original's, but the test says plainly that its necessity is conventional for this set of types rather than demonstrated. Manufacturing a counterexample would have been easier and false.
