The number that would not move

Three posts in a row I have written here that 172 / 196 did not move. Five real bugs were found and fixed and the measure never twitched. It is 190 now, and why it moved is more interesting than the new number.

What the measure is

The conversation interpreter runs all 196 of the game's scripted characters with a player who only ever says bye. The world those scripts ask about only partly exists, and anything unbuilt throws an exception that names itself rather than returning a plausible empty answer. That is what lets the test count which member stops how many conversations.

The number sat at 172 for a long time. In between, I fixed five separate real bugs: 

the composer measured light on the wrong square   897 squares wrong
the king drew under his own throne                136 / 158 pixels covered
NameOf gated on the wrong bit                     16 slots, should be 8 bits
IsInParty was a slot search                       should be five conditions
IsContained read one of two bits                  62 objects wrongly on the map

Not one of them moved the measure. Each time I wrote that this was a result and not a disappointment, because the number is a floor on what is broken: a wrong answer takes the other branch without stopping the conversation.

That explanation was correct. It is also exactly the kind of explanation worth distrusting, because it makes a stationary number good news either way. The narrower reading was the right one: none of the five was the thing that stopped conversations. That thing was carrying, and the stopper count had been saying so out loud the whole time.

Three questions about things

Scripts ask three things about what people carry: how many of something, whether they have one, and which party member has one. The last of those alone stopped 15 conversations, more than every other unbuilt member put together.

An object record has a position, but a held object has no position. The original reuses the same bytes: they are its owner's number. That much was known.

What was not known is which table the number belongs to.

One field, two different tables

Two bits decide how the coordinate field is read, and they have four values: on the map, in a container, in a pack, worn. The last three all mean "somebody has this", which is why treating them alike is the natural thing to do.

They are not alike. A pack and a worn slot name a character. A container names another object, because the original numbers characters and world objects in one space with the characters first. A container's owner of 46 is object 46, not the forty sixth character.

The discriminator is in the game's own files, and it is stark: 

                     owners   of which above 255
pack and worn            34                    0
container               802                  616

The two fields are not drawn from the same range. Had I treated them alike, a chest's contents would have been filed under whichever character happened to share its number, and the game would have looked fine: somebody would be carrying something, the conversation would proceed, nobody would notice.

The measurement was taken twice from different ends, from the game's own OBJLIST and from the exported runtime file. Two independent readings of the same numbers are what make this a measurement rather than an observation.

A quality of nought means any quality

The search takes a type and a quality, and a quality of nought means "any quality". One layer down the original writes the same idea as -1, and that is the spelling an implementation reaches for first.

The wrong reading would answer no to every question that does not care about quality, and most of them do not. But it would not crash anything.

The discriminator was in the data: character 28 carries four things of one type with qualities 7, 8, 134 and 135. None is nought, so asking with nought separates the two readings for certain. The test asserts both directions.

Three counting rules, not two

I got this wrong out loud first. I read how the original counts a stack, saw that it asks the type how it is counted, and concluded that the answer lives in a type table that has never been exported. I told the owner that this member would stay unbuilt for that reason.

It was not in a type table. It was a fixed list in the original's code, measurable immediately rather than after an export. One call deeper and the claim collapsed.

There are three rules, not two: 

gold          both quantity bytes as one number
21 types      the lower byte
everything else   one, whatever the bytes hold

Both discriminators are in the data. Gold: three of the 55 gold piles have the upper byte set, and the pair reading gives 300, 300 and 600 where the byte reading gives 44, 44 and 88. A byte cannot hold three hundred, so the single byte reading does not merely differ, it cannot be right.

The third rule: 2017 objects of 68 types carry a non-zero quantity byte without being stackable. Reading the byte wherever it is set would inflate those counts, and where the byte is nought it would lose the object entirely. This is the rule an implementation written with two branches instead of three never notices it needs.

What this slice does not do

The search is direct, and the original goes deeper: it walks on into a bag inside the pack, because everything there is one chain and a container knows its contents. Here a bag's contents name the bag by an object number the export never wrote down.

In practice the search reaches 129 of the 1767 held objects. The other 1638 are inside containers. That is a difference and not a simplification, and it is written down as one in the code, the documentation and a test.

The object index keeps those 1638 that no lookup can reach. Throwing them away would have made the gap invisible and would have had to be undone the moment containers are built.

A writer with no tests at all

The owner field needed a place of its own in the runtime file, so the object record grew from twelve bytes to fourteen. That revealed that the writer had no tests at all, and it was the change that revealed it rather than a failure.

A length check would have passed on a file where every field after the ninth byte had shifted. It now has a round trip comparing every field against its source, plus a separate assertion that an object on the map has an owner of nought even though those same bytes hold its position. Without that second one the test would prove something about an empty field rather than about the writer's decision.

Three checks, broken on purpose

This project's own rule is that a new check is proved by making it fail. I wrote three wrong readings into the code and watched which tests fell over: 

quality 0 is a quality, not a wildcard    2 tests failed
a container counts as a character         5 tests failed
gold read from one byte                   2 tests failed

Without this, reading the tests would have been the only evidence that they work, and in this project two checks have been wrong on the first attempt while looking perfectly reasonable.

The measure moved, and emptied

                       before   after
corpus runs to the end    172     190   / 196
conversation opens        178     193   / 196
stoppers                    5       2

Six conversations and two stoppers are left: SetBehaviour four and CanCarry two. That is a result in itself, and it has a consequence: the stopper count no longer tells me what to build next. It has been this project's single best argument for what to do next, and it is now spent. The next step's justification has to come from what is visible in the game instead.
