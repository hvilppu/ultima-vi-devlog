Two that are not mirrors

Things can be picked up in the game now. G lifts whatever you are standing on, P puts it back. The first time the world can be done anything to beyond walking across it and talking to it.

Giving and taking

I thought these were one machine pointed two ways. I said so myself in the last post. They are not. 

GiveObj   looks only at DIRECT contents
TakeObj   walks the WHOLE subtree

So a pile inside a bag inside the pack is never merged into, and that same pile can be taken from. The symmetrical implementation is tidier, shorter and wrong.

And wrong in a way nothing reports. The game does not crash, nothing looks broken: things simply stop piling up. You pick up twelve bolts and get a new pile. You pick up more and get a third. There are five piles of bolts in the pack and you wonder why.

A pile fills to 144

A stackable type fills to 0x90, 144, and the rest spills into a new object. The code is unambiguous about it.

I was about to write a check asserting that no pile exceeds 144. I measured first, and just as well: 

stackable objects at the start   1433
exactly 144                        1
above 144                          2
largest                          240

The limit is not a property of the data. It governs what the game hands you, not what the designers placed. Had I enforced it at load I would have corrupted two objects out of the world in the name of a rule that was never about them.

Gold is its own case: one pile, unbounded, and quality does not take part in the match, because for gold it is the upper half of the count. The 21 stackable types match on type and quality, so two qualities stay two piles.

A shared fixture stopped being safe

The most instructive part of this batch was not a rule. It was what happened when I switched on three conversation members.

Seven tests failed at once, and only two of them were about the change I was making.

The cause: the tests share one cached world. That was free for as long as objects were read only. A conversation can give and take things now, so every test that ran one was quietly editing what every later test then measured.

A shared fixture stops being safe the moment what it holds can change, and nothing announces that moment. The symptom is a cluster of failures with no visible connection to each other or to what you did.

The order is newest first

I wrote three tests that assumed a character's things come in the order they arrived. They failed. The order is the other way round, and that is correct: InsertObj links a carried thing immediately behind its owner, so the last thing in is the first thing found.

That is not cosmetic. It is which pile a search hits, so which one is taken from first. I fixed the tests rather than the code, and pinned the order as a test of its own because two others depend on it.

GiveObject, TakeObject and TransferObject answer now. MoveObject still refuses, for one narrow reason: a script's object numbers come from the one numbering space that was never exported. The same gap holds OwnerOf and ObjectTypeOf shut.

What was not built of dropping

The original's CmdDrop is a great deal more than moving an object, and five of its rules need things that do not exist: throwing it further than one square and the breakables that follow from that, the clear line of throw, the three movement points, and the prompt that asks how many. The breakables have a rule of their own: a dragon egg stays on the ground in frame 1 and a mirror in frame 2, everything else disappears.

Picking up is missing the free hand check, the original's "No free hand", because equipment slots do not exist. Two of the four type side effects are in: a candle is put out and an open chest shuts. A moonstone forgetting its moongate and a balloon deflating were left, because they belong to the plot and to vehicles.

Postscript: the same fault, in my own code

The owner tried this in the game and reported it: P does not put anything back. They had picked up type 335, an egg, which is the game's commonest container.

The fault was mine and it is exactly the class this post is about. I stored, for the key to use, the id of the object that had been pointed at. But a pile is picked up by giving and deleting, so that very object stops existing: 

_lastTaken = target.Index;     // the deleted object
IsLive(_lastTaken) == false     // "Nothing to put down."

It worked on a sword, because a single object moves and keeps its id. Not on an egg, a torch, bolts or gold. Right often enough to look like the command works.

I wrote a whole class to separate identity from position, wrote it a test called "an id survives a move", wrote this post about how a position is not an identity, and then used an id the operation itself invalidates in the Unity wiring. The command now reports what the character actually holds through an out parameter, so a caller cannot assume it any more.

Two new tests, proved by putting the old behaviour back for a moment: both fail.
