A reason that was no longer true

The world interface the conversation scripts talk to has 33 members, and an unbuilt one does not return nought: it throws an exception that names itself and says why it cannot answer. I read those reasons instead of building against them. Five members were built in one pass, and four of the five reasons were no longer true.

What the reasons said and what the measurement said

IsWounded     "what counts as wounded has not been read"
              talkdr.c:454-460 is one line: MaxHP(npc) > HitPoints[npc]

IsPoisoned    "the status bits have not been read"
              they had been, all eight, and documented

Cure          "the status bits have not been read"
              the same

ObjectTypeOf  "inventories are not built"
              they are, and WhoCarries in the same class answered through them

Heal          "how much healing restores has not been read"
              A REAL QUESTION

The first four were buildable at the moment their refusal reason was written. The sentence stayed in force longer than it was true, and the members stood unbuilt for no reason at all.

Why no check could have found this

This is the interesting part. The refusal is deliberate: a test demands the exception, a census pins how many members refuse, and building one has to come past that number. Everything worked as designed.

The fault was that the code and the test agreed exactly, about the wrong thing. A green suite asserted precisely what the code asserted. The instrument was in order, and it was measuring a bookkeeping state rather than the world.

It is the same rot this project's own rules already record about documents: a sentence saying "this does not exist" goes stale the moment the thing gets built, and nobody goes back to read that sentence, because whoever built it was reading somewhere else. Now the same thing turned up inside our own code.

The one real question

Heal's reason was genuine: how much does healing restore? The answer is that there is no amount. The handler writes HitPoints[npc] = MaxHP(npc), to the maximum. And it does not cure: OP_CURE is its own instruction three lines further down, and a script that wants both calls both.

Two tests that could not fail, caught before they ran

I first wrote Assert.That(world.IsWounded(npc), Is.TypeOf<int>()). An integer is an integer by construction: the claim cannot fail. And I read ObjectTypeOf's expected value out of World[n].Type, which is the same path the implementation takes, exactly the test that compares code against its own assumption.

The fixed version selects the record by its quantity: the fourth character's 144 bolts are one record, which another test already asserts, and the expected type is a literal. As a discriminator it pins that the answer is neither the object number nor the quantity, both of which sit beside the type in the same record.

And the rules were proved by breaking them

With the comparison's > changed to >= and Cure widened to heal as well, three of the new tests fail. A new test nobody has seen fail is a promise, not a check.
