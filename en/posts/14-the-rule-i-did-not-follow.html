Ultima VI rebuilt

Notes from a 1:1 reimplementation in C# and Unity.

← all posts · 14

The rule I did not follow

The plan has said from the start that the game logic stays independent of Unity. I did not follow it, and nothing reminded me until the bill arrived.

The architecture section of this project carries one principle in bold:

Key principle: U6Engine must not reference the UnityEngine namespace. The game logic is then runnable in a console test at thousands of turns a second, which is the only practical way to validate the combat and AI rules against the original.

That assembly did not exist. I had written the map, collision, doors, the clock, lighting, the random number generator, the combat formulas and character development all into the same U6Runtime assembly as the Unity drawing code. Every individual file was a small and sensible decision at the time. Together they were the plan being broken.

The bill

Debt is invisible until it is collected. Here the collection came during the previous post: I could not get Unity's batch runner to execute the tests, on three separate attempts, and not one rule could be run without the editor. Seventy nine new tests about combat and character development were hostages to it.

Preventing exactly that is why the principle was written. Its purpose was never tidiness but runnability, and that part got proved the hard way.

The split was cheap because the code already qualified

I measured before starting: 19 files out of 22 referenced Unity nowhere at all. The move was mechanical, not a rewrite. Three stayed on the Unity side: the view component, the palette conversion and the path discovery.

The important part was not the move but that the principle is now enforced by the build from two directions: 

Inside     U6Engine.asmdef  "noEngineReferences": true
Unity      -> a reference to Unity fails the compile

Outside    Tools/U6Engine/U6Engine.csproj
Unity      -> compiles the same files with no Unity libraries present

That same project also subjects the Unity code to the quality gate used on the tooling side: nullable, analysers, warnings as errors. Unity's own compiler does none of that.

What the compile found immediately

The first attempt failed on three real couplings nobody had noticed. All three were the same kind: game data that had drifted into Unity code.

The palette. U6GameData was building Unity Color32 arrays. I split it: the engine reads and validates the bytes, the Unity side converts them for drawing once at load instead of per pixel. The conversion left the drawing loop as a side effect.

The start position and the Avatar's tile number. These sat as constants on the view component. They are game data, not rendering, and moved to a class of their own. The test that checks the game does not begin inside a wall no longer needs an editor to find out where the game begins.

Path discovery. The engine now decides whether a directory holds an export, and Unity tells it where Unity keeps things. The test helper finds the export by walking up the directory tree, which works in the editor and in a console run alike.

Coverage that was not there

Running the coverage check against the new structure turned up one more thing, and it is a good example of a measure telling you what you want to hear.

U6View had always counted as covered. It counted because tests referenced it to fetch the start position constants. When those constants moved away, the coverage went with them, and it became clear that no test has ever executed a line of its own code.

It is a MonoBehaviour whose startup only runs in play mode, so a meaningful test needs a scene. I recorded it as a gap rather than fixing it: the wrong fix would have been a test that looks like coverage without running anything, which is precisely the situation just escaped.

Three errors that reached the owner's editor

The move itself was mechanical. Verifying it was not. Three compile errors got through, one at a time, and each had the same cause: my check covered less than I reported it covering.

First I wrote a Unity-only test I could not run, and published it anyway. Then the compile check covered the scripts but not the test assembly, and I still reported "the Unity side builds". Third, renaming an assembly left a dangling reference in U6Editor.asmdef, and that could not surface because the check compiled everything into one assembly. Inside a single assembly everything is visible to everything, so a missing assembly reference is structurally invisible.

The fix is therefore structural rather than cosmetic: there is now one check project per asmdef, with exactly the references the asmdef declares, plus a script that verifies every asmdef reference points at an assembly that exists. 

U6Engine.csproj              engine, with no Unity at all
U6Unity.Check.csproj         -> U6Engine + InputSystem
U6Editor.Check.csproj        -> U6Engine + U6Unity + UnityEditor
U6EditModeTests.Check.csproj -> U6Engine + U6Unity + nunit
CheckAsmdefs.ps1             references resolve to something real

The same kind of mistake as the earlier coverage check, anchored at the start of a line and blind to indented types. In both cases the measure told me what I wanted to hear.

Tests

The rules now run under dotnet test, in a second, with no editor: 

U6Engine.Tests    274 / 274   without Unity
U6Formats.Tests   266 / 266
U6Export.Tests     32 / 32

Five tests stay on the Unity side, and they are exactly the ones that check the Color32 conversion. That is the right split: Unity is needed for what Unity actually does.

I also wrote down the rule that follows from this: do the structural work before writing more on top of it. "It will be easy to move later" is the sentence that has now cost something once.
