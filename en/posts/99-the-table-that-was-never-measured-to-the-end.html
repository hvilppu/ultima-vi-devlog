The table that was never measured to the end

The owner crashed the game by walking a character through a town. The close-enough test's own table was measured for run bytes 4 to 15 and refused everything else by throwing; run byte 17 landed on that refusal in the middle of an ordinary walk. Refusing was the right instinct. The measured range was simply the wrong size.

A run byte is a byte

__DoOnPath indexes the direction table DirIncrX/DirIncrY with the raw run byte, never with the direction alone, and both tables are eight bytes each. 4 to 15 was never the right bound: it was the part somebody had needed so far. A run byte's bottom two bits are its direction and the rest is a step count that alone reaches 63, and a run byte is a byte, so the lookup can be asked for anything from 0 to 255.

The same sixteen bytes twice, and the discriminator that told them apart

The sixteen byte run DirIncrX and DirIncrY form together occurs twice in the owner's own GAME.EXE, so content alone does not settle which one is real. The discriminator is what follows each match: after the real base, the next eight bytes read as a pointer table that rises in steady steps, to the eight direction name strings; after the other candidate, they neither rise nor space out regularly. Both sides are a test now: the real base scores well, the other candidate scores badly, and the swapped order of the sixteen bytes matches neither place at all.

No bound, no default

The fix is not to soften the refusal, it is to finish measuring. The table now covers the whole byte, 0 to 255, and run byte 17, the owner's own crash, reads (2, 2) and throws nothing. The original reads past its own table into whatever memory follows it; the port reads exactly as far past its own, not an inch less and not an inch more.

Measured, not guessed: how far a run actually walks

Covering the table left open a question nothing had needed to answer before: how large a step count actually shows up in the owner's own real schedule data. The whole path search was run against the real map and the real schedule book, every weekday and every hour, and the largest step count in any resulting run was 22. Far from the run byte's own 63, further still from 255, because the path search's own 40 by 40 window bounds how long a single straight run can practically get.

What this does not cover

The rest of the table is the linker's own neighbouring data: file names, an error message format string, the direction names themselves. These values belong to the owner's own build rather than to Ultima VI as such, and a different build would give different numbers in the same run bytes. Written down plainly: the original's own fault, not this port's.
