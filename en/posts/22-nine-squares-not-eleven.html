Nine squares, not eleven

Characters are on the map. The rule for what counts as being on screen turned out to be more particular than I expected, and one part of it is not a filter even though it looks like one.

The conversation scripts ask the world 2563 questions, and the most asked of them is fetching a party member: 549 times. When I measured the second operand, the number split like this: 

542 calls   only members on screen
  7 calls   any member

So the most called member of the whole interface does not need a party list. It needs to know where everyone is standing. The rough call count had told me "party next", and the closer measurement said something else entirely.

The box is not the window

The game draws eleven squares by eleven. I assumed "on screen" meant that.

It does not. The comparison is strict on both sides of five, so the counted box is nine squares and the window's outer ring is drawn but does not qualify. A character standing visibly at the edge of the view is not on screen.

Nor is that all. The square has to be showing something as well: an object is there, or its tile is an object tile, or the tile is neither hidden nor darkness. A character behind a wall is close by coordinates and not on screen.

The level is not compared

The original compares the column and the row and nothing else. A character standing in the same place on a different level passes the position test.

I do not know whether that can happen in play and did not go and find out now. I reproduced it as it stands and wrote a test saying so, because otherwise a signature with no level in it looks like an oversight rather than a decision.

A squeeze that is not a filter

This is the part I would certainly have got wrong had I reasoned from the name.

When a script asks for "on screen member number one", it does not mean "place one, if it is on screen". The original builds a shorter list of the ones that are on screen first, and indexes that. 

party        1  2  3  4
on screen       2     4
squeezed     2  4

index 0  ->  2
index 1  ->  4      the naive reading would give nought

I implemented the naive reading on purpose to see whether my tests could tell the difference. Two failed, exactly the two that pin this.

A smaller note from the same place: nought is a real character number, and the original also answers nought for "nobody there". A script cannot tell "character nought" from "nobody" apart. That is the original's answer and it stays.

The Unity check caught one

I wrote Does.Not.Contain(5) in a test. The headless run accepted it, but the Unity check project failed: in the NUnit that Unity ships, that resolves to the string overload rather than the collection comparison.

This would have reached the editor without the check. It is the same class of fault those projects exist for: code that compiles here and not there, with the difference somewhere other than what you were writing.

Next is the first clean implementation slice

The visibility half needs the composer to say which tile ended up on a square and whether an object was drawn there. The composer works both out already, darkness included, but produces nothing but pixels.

The rule is read and all three constants are known, so nothing is left unmeasured. This week I wrote a rule into the project instructions about which work belongs to which model, and this is the first slice that lands on the implementation side from start to finish.

After that comes a number I promised and do not yet know: once the world can answer, the corpus test can run all 199 conversations and say how many actually get through. I expect it is not 199, because object calls are 28 per cent and are not built. But a guess is a guess, which is why it gets measured.
