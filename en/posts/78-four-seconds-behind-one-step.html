Four seconds behind one step

Not a slice, and not the original's fault: a performance defect in this project's own code, found by the owner in play rather than by any test. A direction key moved the party about four seconds after it was pressed. Every one of the 2031 tests that existed at the time passed, because none of them measures how long anything takes.

A helper that rebuilt the whole world on every single change

U6ObjectWorld keeps three lookup dictionaries, by square, by owner and by container, so a renderer or a search never has to scan all sixteen thousand objects by hand. Nine different mutations, Create, Destroy, MoveTo, PutInside and five others, kept those three dictionaries correct the same way: clear all three and walk the entire chain from the front, rebuilding every bucket from scratch. Against the owner's own exported data, 16838 objects, one call to that rebuild cost about 1.5 milliseconds.

Harmless for years, until something called it in a loop

A linear helper is not a defect by itself. It was correct, it was tested, and it stayed cheap enough to ignore for as long as nothing in the game actually mutated the object world very often: a player walks one step at a time, and one step never used to create or move dozens of objects. Two of M14's own slices changed that without anyone measuring the cost. Eggs now hatch as the party walks (slice F6), and every creature an egg hatches is immediately given its own possessions (slice F5), and every possession is one more call into the same rebuilding helper. One step across an area boundary can hatch several eggs at once, each with its own creatures and their own gear, so a single key press turned into hundreds of rebuilds, each walking the whole world. Hundreds of 1.5 millisecond rebuilds is the four seconds.

The fix is incremental bookkeeping, not a smaller rebuild

U6ObjectWorld's three dictionaries are incremental now. A create puts its own record straight into its own bucket. A destroy takes it back out. A move carries a whole subtree from one bucket to another rather than rebuilding either one. The full rebuild still exists, because the file loading path genuinely does need to build all three buckets once from nothing, and the constructor is now its only caller. Measured the same way as before, on the same 16838 object export: 0.017 milliseconds a create, about eighty-eight times faster by the same stopwatch that found the problem.

One rule had to survive the change exactly: a newly placed object goes in front of whatever already stands on its square, not behind, because four of the party-ring spells depend on that order to find the right target first. Every incremental insert this fix makes is a prepend for exactly that reason, proven by the same invariant checks the object world already carried.

A second, smaller version of the same mistake

U6View read and parsed a JSON table from disk, the creature class table and the possession table, on every single call that needed either one: the walking step and all three hit application paths. Neither table changes while the game runs, so both are read once now and kept, which removes a disk read and a parse from the hottest path in the game.

What a passing suite cannot tell you

Every test in this project's own suite asks whether an answer is right. None of them asks what it cost, because nothing before this counted work or measured time at all. That is not a gap this single fix closes: it is a second kind of question this project has never asked of itself, and it needed the owner actually playing the game to surface it. The shape is worth keeping: a helper that is linear in the whole data structure is cheap only as long as nobody calls it often, and nothing about the helper itself changes the day that stops being true.
