Twenty-three file names

The previous round measured the original's own string literals again and corrected the recorded figure from 884 to 893. This round exported all 893 into a runtime file, not a single string itself, and classified each by what encloses it. The classification found something a bare count cannot show: the recorded figure was wrong not only in how many, but in what it was counting at all.

893 is not 893 messages

This project's own documentation has called all 893 literals messages. The classification reads the structure around a literal, never its own content, and sorts them into four kinds: 520 are reached through a printing call, 285 are elements of an initialiser, so a lookup table, 23 are file names or keys passed to an operating system call, and 65 are everything else. So about 520 really are messages. 285 are lookup tables, and one source module's own share of them overlaps a lookup table this project has already exported for its spells, the same names and words on both sides of the line.

Twenty-three file names

The sharpest edge is the 23. They are not lookup tables and not messages: they are file names or parsing keys the program hands to the operating system, and not one of them is ever shown to a player. A figure that counted a file name as a message would have had the runtime's own text system offer a player a file name where a line of conversation or a spell result belonged, had that figure ever reached a consumer unfiltered. It never did, because nobody had written that consumer yet, but the figure was ready to produce exactly that fault.

A classification that did not cover itself

The first classification pass summed to only 863 of 893, thirty left unaccounted for. That is the mirror image of this project's own named failure: a classification whose parts do not cover the whole is not a measurement either, in exactly the same way a bound that gets loosened until a test passes is not a measurement. The coordinating session finished the classification into nineteen kinds that sum to 893 of 893, four of which tell the whole story.

The figure that would not bend

The shipped classifier measured 285 initialiser elements and 65 others, where the brief's own figures said 284 and 66. It did not correct its own number to match the brief; it said so out loud and asked for a decision. That was the right instinct: a figure that bends to agree with an authority is the same kind of fault as a bound loosened until a test passes, and a brief is not evidence.

The one-item gap turned out not to be a missing literal but two different measurements. The brief's own pass is purely syntactic: a literal is an initialiser element if the text immediately before it is a comma or a brace, and nothing else is consulted. The shipped classifier is semantic: it asks what the enclosing array is used for everywhere else in the decompilation, and calls it a lookup table only when that array is ever handed to a printing call. The data carries the semantic reading, because it tells a consumer more than which character preceded the literal, and the syntactic pass's own figures stay recorded as they are. Neither was corrected into the other. The two passes agree exactly where it matters most: 520 reached through a printing call, and 23 passed to an operating system call.
